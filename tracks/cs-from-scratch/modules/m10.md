# m10 — Databases foundations

## L1 — The relational model: tables, rows, columns

**Concept.** A **relational database** stores data in **tables**. Each table models one kind of thing (users, orders, products). A table has **columns** (the fields — `id`, `name`, `email`) with a fixed type each, and **rows** (one record — one user). This tidy grid is the "relational model," and you query it with **SQL** (`SELECT name FROM users WHERE id = 7`). The structure is defined up front (the **schema**), which keeps data consistent: every user row has the same shape.

**ELI5.** A table is a spreadsheet with rules. Columns are the headers across the top; each row is one entry; and unlike a free-form spreadsheet, the database enforces that the "age" column really holds numbers and every row fits the same template.

**Deep dive (optional).** "Relational" refers to the tables (mathematically, *relations*), not to relationships between tables — a common mix-up. Relational databases (PostgreSQL, MySQL, SQLite) dominate when data is structured and consistency matters. **NoSQL** databases (document, key-value, graph stores) trade the rigid schema for flexibility or scale; useful, but out of scope for this survey beyond knowing they exist.

**Build-task tie-in.** Picture a `users` table:

| id | name | email |
|----|------|-------|
| 1  | Ada  | ada@example.com |
| 2  | Alan | alan@example.com |

`SELECT * FROM users WHERE id = 2` returns exactly Alan's row. Reading SQL as "pick these columns from this table where this is true" is most of day-one database literacy.

**Check.** Learner can describe a table as rows (records) and columns (typed fields), and that a schema fixes the shape.

## L2 — Keys and relationships

**Concept.** A **primary key** is a column (often `id`) whose value **uniquely identifies each row** — no two rows share it, so it's the reliable way to point at exactly one record. A **foreign key** is a column in one table that holds the primary key of a row in *another* table, creating a **relationship**. That's how data stays un-duplicated: an `orders` table doesn't copy the customer's whole details into every order — it just stores the customer's `id` as a foreign key, and you **join** the tables to combine them when needed.

**ELI5.** A primary key is everyone's unique membership number. A foreign key is writing that membership number on a form instead of recopying the person's whole profile — one number links back to the full record.

**Deep dive (optional).** This "store it once, reference it by key" approach is **normalization**: it avoids duplicated, drift-prone data (change an email in one place, not in a thousand order rows). The database can also enforce **referential integrity** — rejecting an order whose `customer_id` doesn't match any real customer — so relationships can't silently break.

**Build-task tie-in.** Two tables linked by a key:
```
users(id, name)                     -- id is the primary key
orders(id, user_id, total)          -- user_id is a foreign key → users.id
```
"Which orders are Ada's?" = find Ada's `id` in `users`, then the `orders` rows whose `user_id` matches. That matching is a **join**.

**Check.** Learner can explain that a primary key uniquely identifies a row and a foreign key references another table's primary key to relate them.

## L3 — Indexes: why some queries are fast

**Concept.** Without help, finding rows that match a condition means the database scans **every row** — O(n), slow on big tables. An **index** is a separate, sorted lookup structure (usually a **B-tree** — recall balanced trees from m5) built on a column so the database can jump to matching rows in about **O(log n)** instead of scanning everything. The trade: indexes take extra disk space and make **writes** a bit slower (every insert/update must also update the index). So you index the columns you frequently search or join on — not every column.

**ELI5.** An index is the index at the back of a book. To find every mention of "recursion" you *could* read all 500 pages (a full scan), or flip to the back index and jump straight to the right pages. Building that index took effort and paper, but every future lookup is instant.

**Deep dive (optional).** A primary key is automatically indexed (that's partly why key lookups are fast). An index is **not a copy of the table** — it's a compact, ordered map from column values to row locations, a common misconception. Over-indexing is a real cost: more storage, slower writes, and indexes that are never used for reads just slow the database down.

**Build-task tie-in.** On a million-row `users` table, `SELECT * FROM users WHERE email = ?` crawls without an index (checks every row) and is near-instant with one on `email`. `CREATE INDEX idx_email ON users(email)` is you buying O(log n) lookups with a little space and write cost.

**Check.** Learner can explain that an index speeds up lookups (roughly O(n) scan → O(log n)) at the cost of space and slower writes, and that it isn't a copy of the table.

## L4 — Transactions & ACID

**Concept.** A **transaction** groups several database operations so they succeed or fail **as one unit** — all of them, or none. The classic case is a bank transfer: debit account A *and* credit account B must both happen; a crash in between must never leave money debited but not credited. Databases guarantee this with **ACID**:
- **Atomicity** — all-or-nothing; a transaction fully completes or fully rolls back.
- **Consistency** — it moves the database from one valid state to another (constraints like keys and types stay satisfied).
- **Isolation** — concurrent transactions don't see each other's half-done work; the result is as if they ran one at a time.
- **Durability** — once a transaction **commits**, its changes survive even a crash or power loss.

**ELI5.** A transaction is a "do all of this or pretend I never started" wrapper. Think of moving money between two jars: ACID promises you never end up with the cash out of one jar and not in the other, even if the lights go out mid-move, and that nobody peeking sees a half-done move.

**Deep dive (optional).** Isolation is the subtle one: without it, two transactions running at once (recall concurrency, m8) can interfere and corrupt data, so databases use locks or versioning to keep them from stepping on each other. ACID is the relational world's strong promise; some large-scale distributed/NoSQL systems relax parts of it (often weaker isolation or "eventual consistency") to go faster or scale wider — a deliberate tradeoff, not a free lunch.

**Build-task tie-in.** In SQL: `BEGIN;` … the debit … the credit … `COMMIT;`. If anything fails before `COMMIT`, a `ROLLBACK` undoes the whole group as if it never ran — atomicity you can see.

**Check (mastery bar for m10).** Learner can explain primary vs. foreign key, what an index buys and costs, and what a transaction guarantees (all-or-nothing, with ACID in their own rough words).
