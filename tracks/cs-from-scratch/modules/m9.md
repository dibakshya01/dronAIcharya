# m9 — Networking & the web

## L1 — IP addresses and packets

**Concept.** Computers on a network find each other by **IP address** — a numeric label like `192.0.2.10` (IPv4) or a longer `2001:db8::1` (IPv6). Data doesn't travel as one big stream; it's chopped into small **packets**, each stamped with the source and destination IP, and sent across the network independently. **Routers** between you and the destination read each packet's address and forward it onward, hop by hop, until it arrives. Packets can take different paths and arrive out of order — sorting that out is the next layer's job.

**ELI5.** An IP address is a postal address for a computer. A big message is mailed as a stack of postcards (packets), each with the destination written on it. The postal network (routers) relays each postcard toward the address; they don't need the whole message to move one card.

**Deep dive (optional).** IPv4 has ~4.3 billion addresses — not enough for today's devices — which is why IPv6 (vastly more) exists and why home networks share one public IP across many devices (NAT). IP itself is "best effort": it tries to deliver packets but makes no promise they arrive, arrive once, or arrive in order.

**Build-task tie-in (standalone).** Run `ping example.com` in a terminal: it sends small packets and reports the round-trip time and any losses. That round-trip number *is* packets going out and coming back across routers.

**Check.** Learner can say an IP address identifies a device and that data crosses the network as individually-addressed packets.

## L2 — TCP vs UDP (intuitively)

**Concept.** On top of IP sit two common ways to send packets. **TCP** sets up a connection and guarantees **reliable, in-order** delivery: it numbers packets, confirms receipt, and resends anything lost — at the cost of some overhead and delay. **UDP** is **fire-and-forget**: no connection, no guarantees, no resending — just fast, lightweight packets. Neither is "better"; they're different tradeoffs. TCP for when every byte must arrive correctly (web pages, files, email); UDP for when speed beats perfection and a dropped packet is no disaster (live video, voice calls, games, DNS lookups).

**ELI5.** TCP is a phone call with constant "got it, go on" — nothing is missed, but there's handshaking overhead. UDP is shouting across a noisy room: fast and cheap, but if a word gets lost, oh well, you keep going.

**Deep dive (optional).** TCP's reliability comes from the handshake (SYN/ACK) to start, sequence numbers, acknowledgements, and retransmission — great for correctness, but the resending-and-waiting can add lag. For live media a late packet is useless anyway (the moment has passed), so UDP's "drop it and move on" actually gives a *smoother* experience. Much of the modern web layers reliability on top of UDP itself for lower latency, but the TCP-vs-UDP tradeoff is the durable idea.

**Build-task tie-in (standalone).** No code needed: classify examples. Downloading a file → TCP (a missing byte corrupts it). A choppy video call → UDP (better a skipped frame than everything freezing to re-fetch it). Making those calls yourself cements the tradeoff.

**Check.** Learner can contrast TCP (reliable, ordered, slower) with UDP (fast, no guarantees) and name a good use of each.

## L3 — DNS: names to numbers

**Concept.** People remember `example.com`, but computers connect to IP addresses. **DNS** (Domain Name System) is the internet's directory that **translates a domain name into an IP address**. When you use a domain, your computer asks a DNS resolver "what's the IP for this name?", gets an address back, and *then* connects to that address. DNS is the lookup step; the IP is the actual destination — they are not the same thing.

**ELI5.** DNS is the phone book (or your phone's contacts). You know the *name* "Mom"; DNS is what turns that name into the actual *number* your phone dials. The name is for you; the number is what the network needs.

**Deep dive (optional).** DNS is a distributed hierarchy: resolvers ask root servers, then the `.com` servers, then the domain's own servers, caching answers along the way so repeat lookups are instant. A domain can map to multiple IPs (for load balancing / redundancy), and changing where a domain points is just updating its DNS records.

**Build-task tie-in (standalone).** `nslookup example.com` (or `dig example.com`) shows the IP a name resolves to — you're doing by hand the lookup your browser does silently before every visit.

**Common misconception to retire.** "DNS is the website's address." No — DNS is the *lookup system* that *finds* the address (the IP). Mixing them up is the classic error here.

**Check.** Learner can explain DNS turns a domain name into an IP address, and that DNS (the lookup) and the IP (the destination) are different.

## L4 — HTTP and how a page loads

**Concept.** The web runs on **HTTP** (and its encrypted form **HTTPS**), a simple **request/response** conversation. Your browser (the **client**) sends a **request**: a method (`GET` to fetch, `POST` to send data), a path (`/about`), and some headers. The **server** sends back a **response**: a **status code** (`200` OK, `404` Not Found, `500` server error), headers, and usually a body (the HTML). HTTP is **stateless** — each request stands alone — so sites use cookies/tokens to remember you across requests.

**ELI5.** It's ordering by mail. You send a slip: "please send me the /about page" (request). The shop mails back a parcel with a status sticker — "here you go (200)" or "no such thing (404)" — and the contents (response). Each order is independent; the shop needs your membership card (cookie) to know it's you again.

**Deep dive (optional).** Putting the whole module together, here's what happens when you open `https://example.com`:
1. **DNS** (L3) resolves `example.com` to an IP.
2. Your browser opens a **TCP** (L2) connection to that IP, and for HTTPS negotiates **TLS** encryption.
3. It sends an **HTTP GET** request for the page.
4. The server responds with **HTML** (and a status code).
5. The browser parses the HTML, discovers it needs more files (CSS, JavaScript, images), and fires off **more requests** for each.
6. It assembles everything and **renders** the page.

**Build-task tie-in.** `curl -i https://example.com` prints the raw response — status line, headers, and HTML body — exactly what your browser receives but usually hides. In Python, `requests.get(url).status_code` and `.text` show the same request/response pair.

**Check (mastery bar for m9).** Learner can trace, at a high level, URL → DNS lookup → TCP/TLS connection → HTTP request → server response → render, and explain request/response with a status code.
