# m6 — Algorithms & Big-O

> An algorithm is a step-by-step recipe to solve a problem. Big-O is how we compare recipes without a stopwatch.

## L1 — What "complexity" means (steps, not seconds)

**Concept.** When we ask "how expensive is this algorithm?", we don't mean how many seconds it takes — that depends on your machine, the language, the weather. We mean: **as the input grows, how fast does the amount of work grow?** We count *steps* (comparisons, operations) as a function of input size **n**. **Big-O notation** captures the shape of that growth and deliberately ignores constant factors and small terms, because for large inputs the growth *shape* is what decides whether something finishes in a blink or never.

**ELI5.** It's miles-per-gallon for code, not the length of one trip. You're asking "if the road gets twice as long, how much more fuel?" — not "how many minutes was today's drive?"

**Deep dive (optional).** Why ignore constants? Because "3n + 50" and "n" grow the same *shape* — a straight line — and for big n the n term dominates. Big-O keeps the dominant term and drops the rest: `3n² + 100n + 7` is just **O(n²)**. It's a tool for comparing how things *scale*, not for predicting exact runtime.

**Build-task tie-in.** A loop that looks at every item once does n steps → O(n). A loop inside a loop, each over all items, does about n×n steps → O(n²). You can *see* the step count by counting how deep the loops nest.

**Check.** Learner can say complexity is about how work grows with input size, measured in steps, not wall-clock seconds.

## L2 — The common classes: O(1), O(log n), O(n), O(n²)

**Concept.** A handful of growth shapes cover most code. In order from best to worst as n grows:
- **O(1) constant** — same work no matter the size (look up `array[i]`, read a dict key).
- **O(log n) logarithmic** — work grows *very* slowly; each step throws away half the remaining input (binary search, balanced-tree lookup). Doubling n adds just *one* step.
- **O(n) linear** — work grows in step with size; look at every item once (scan a list). Double n → double the work.
- **O(n²) quadratic** — work grows with the square; every item compared with every other (naive nested-loop comparisons). Double n → *four times* the work.

**ELI5.** O(1): grabbing the top book off a stack — same effort for a pile of 10 or 10,000. O(log n): finding a word in a dictionary by splitting it in half again and again. O(n): reading every page once. O(n²): comparing every page with every other page — it explodes as the book gets thicker.

**Deep dive (optional).** O(n log n) sits between linear and quadratic and is the speed of good sorting algorithms (merge sort, the sorts behind `sorted()`). The gap between classes is enormous at scale: for n = 1,000,000, O(log n) ≈ 20 steps, O(n) = a million, O(n²) = a *trillion*. That difference is "instant" vs. "come back next week."

**Build-task tie-in.** Binary search shows O(log n): to find a number in a *sorted* list of a million, you check the middle, halve, repeat — about 20 checks, not a million. Searching an *unsorted* list has to check each item → O(n).

**Check.** Learner can order O(1) < O(log n) < O(n) < O(n²) by growth and give an everyday example of each.

## L3 — Reading and comparing Big-O in practice

**Concept.** In real use, Big-O helps you answer "will this still be fast when my data gets big?" and "which structure/algorithm should I pick?" You usually quote the **worst case** (an upper bound on growth), though average case matters too (recall hash maps: average O(1), worst O(n)). The practical skill is reading code and naming its shape: no loop over the input → often O(1); one pass → O(n); nested passes → O(n²); repeated halving → O(log n).

**ELI5.** You don't need to compute the exact number of steps. You glance at the recipe and ask, "if my guest list doubles, does the cooking double, quadruple, or barely change?"

**Deep dive (optional).** Two honest caveats. First, Big-O hides constants, so for **small** n a "worse" Big-O can actually be faster (a simple O(n²) can beat a fancy O(n log n) on tiny inputs). Big-O is about *scaling*, so it matters most when n is large. Second, there's also **space complexity** — how memory grows with input — measured the same way; sometimes you trade more memory for less time (a hash map uses extra space to buy O(1) lookups).

**Build-task tie-in.** Revisit m4/m5 through this lens: `list.index(x)` is O(n) (scan), `dict[key]` is O(1) (hash), `x in sorted_list` via binary search is O(log n). The data structure you chose *is* the Big-O you get.

**Common misconception to retire.** "O(n²) means it takes n² seconds" — no. Big-O is a growth rate with the units and constants stripped out; it tells you how runtime *scales*, not what the clock will read.

**Check (mastery bar for m6).** Learner can rank O(1)/O(log n)/O(n)/O(n²) by growth, read a simple function and name its class from its loops, and explain that Big-O measures growth, not seconds.
