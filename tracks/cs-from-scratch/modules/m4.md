# m4 — Data structures I: arrays & lists

> A data structure is just an agreed way to lay out data in memory so some operations are cheap. The layout *is* the tradeoff.

## L1 — Arrays: a contiguous row of boxes

**Concept.** An **array** is a block of memory holding elements of the same size, laid out back-to-back with no gaps. Because they're contiguous and evenly sized, the computer can find element `i` with one calculation — `address = start + i × element_size` — and jump straight there. That's why reading or writing `array[i]` is **O(1)** ("constant time"): it costs the same whether the array has 10 items or 10 million. The catch: a classic fixed array has a fixed size decided up front.

**ELI5.** An array is a row of identical, numbered lockers bolted together. To reach locker 500 you don't walk past the first 499 — you know exactly how far down the wall it is and go straight there.

**Deep dive (optional).** "Contiguous" also makes arrays friendly to the CPU **cache**: fetching one element pulls in its neighbors, so scanning an array in order is fast. This cache-friendliness is a big reason arrays are the workhorse structure in practice, beyond the Big-O on paper.

**Build-task tie-in.** `nums = [10, 20, 30, 40]; nums[2]` → `30`, instantly. Index access doesn't loop through the earlier items — it computes the location and reads it.

**Check.** Learner can explain that arrays store elements contiguously and that indexing is O(1) because the location is computed, not searched.

## L2 — Dynamic arrays (Python lists, JS arrays)

**Concept.** Real languages give you a **dynamic array**: an array that grows as you add items. Behind the scenes it holds a fixed block with some spare room; when it fills, it quietly allocates a bigger block and copies everything over. Most appends are O(1); the occasional copy is O(n), but it happens rarely enough that appending is **amortized O(1)** (cheap on average). Indexing stays O(1). But inserting or deleting in the *middle* is **O(n)**, because every later element has to shift over to keep the row contiguous.

**ELI5.** It's the locker wall from L1, but the building super adds a bigger wall and moves your stuff when you run out of lockers. Adding to the end is easy; squeezing something into the middle means sliding everyone down one locker.

**Deep dive (optional).** Python's `list` and JavaScript's `Array` are dynamic arrays, **not** linked lists — a common mix-up. That's why `list.append(x)` and indexing are fast, while `list.insert(0, x)` and `list.pop(0)` are slow (everything shifts). Growing by a multiplier (e.g. doubling capacity) is what makes appends amortize to O(1).

**Build-task tie-in.** Time it:
```python
big = list(range(1_000_000))
big[500_000]      # instant — O(1) index
big.append(1)     # fast — amortized O(1)
big.insert(0, 1)  # slow — O(n), shifts a million items
```
Feeling `insert(0, ...)` lag on a big list makes "O(n) shifting" concrete.

**Check.** Learner can explain that a dynamic array resizes by copying, that append is amortized O(1), and that middle inserts/deletes are O(n).

## L3 — Linked lists and the cost of operations

**Concept.** A **linked list** stores each element in its own little **node** that also holds a pointer (reference) to the next node. The nodes can live anywhere in memory — not contiguous. That flips the costs: once you're *at* a node, inserting or removing is **O(1)** (just re-point a couple of links), and adding to the front is cheap. But there's no address math, so reaching the *i*-th element means walking from the start — **O(n)** — and you pay extra memory for all those pointers.

**ELI5.** A linked list is a treasure hunt: each clue tells you where the next clue is. Splicing a new clue into the chain is easy, but to reach clue #500 you must follow clues 1→2→3… all the way there.

**Deep dive (optional).** Array vs. linked list is the first real "pick your tradeoff" moment:

| Operation | Array / dynamic array | Linked list |
|---|---|---|
| Index (get the *i*-th) | O(1) | O(n) |
| Insert/delete at end | amortized O(1) | O(1) |
| Insert/delete in middle | O(n) (shift) | O(1) *once you're there* |
| Memory locality / cache | great | poor |

In everyday code, dynamic arrays win most of the time (cache-friendliness and simple indexing matter a lot), which is why `list` is the default. Linked lists shine when you're constantly splicing at known positions and rarely index.

**Build-task tie-in (standalone).** You rarely build a linked list by hand in Python (the built-in `list` is a dynamic array; `collections.deque` covers fast ends). Sketch three nodes — `A→B→C` — on paper and show that inserting `X` between `A` and `B` just changes two arrows, versus an array shifting everything right.

**Check (mastery bar for m4).** Learner can explain *why* indexing an array is O(1) but inserting in the middle is O(n), and contrast that with a linked list's cheap splicing but O(n) indexing.
