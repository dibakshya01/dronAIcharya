# m1 — How computers represent data

> Lesson content for the `teach` skill. Teach one lesson at a time, at the learner's level, then check. Don't dump the whole file at them.

## L1 — Bits and bytes: everything is 0s and 1s

**Concept.** At the bottom, a computer stores everything — numbers, text, images, sound, your code — as **bits**. A bit is a single 0 or 1 (think: a tiny switch, off or on). Bits are grouped into **bytes** of 8 bits. With 8 bits you can make 2⁸ = 256 different patterns, so one byte represents one of 256 values (0–255). Bigger things are just more bytes.

**ELI5.** Imagine a huge wall of light switches, each either off (0) or on (1). Every photo, song, and sentence on your computer is really just a particular pattern of those switches. "Byte" is just the habit of reading them 8 switches at a time.

**Deep dive (optional).** Why 8? It's a historical convention that stuck; 8 bits conveniently covers the basic Latin character set and is a power of two. "Kilobyte/megabyte/gigabyte" are roughly thousands/millions/billions of bytes (strictly, powers of 1000 for KB/MB or 1024 for KiB/MiB — the units are often used loosely).

**Build-task tie-in.** In Python, `len("hello".encode("utf-8"))` is `5` — five bytes, one per letter here. Try `"hi".encode("utf-8")` → `b'hi'`, two bytes. You're seeing the actual byte count of the text.

**Under the hood.** Those bits are physical: tiny charges in RAM, magnetic/flash states on disk. The computer never sees "the letter A" — it sees a byte pattern that software agrees *means* A.

**Check.** Learner can say a bit is a 0/1, a byte is 8 bits, and one byte holds one of 256 values.

## L2 — Binary and hex: base 2 and base 16

**Concept.** The numbers we write (247) are **base 10**: digits 0–9, place values of ones, tens, hundreds. Computers work in **binary (base 2)**: digits 0 and 1, place values 1, 2, 4, 8, 16… So `11110111` in binary is 128+64+32+16+0+4+2+1 = 247. Because long binary is hard to read, we often use **hexadecimal (base 16)**: digits 0–9 then a–f (where a=10 … f=15). The handy part: one hex digit is exactly 4 bits, so **two hex digits = one byte**. 247 is `0xF7`.

**ELI5.** It's the same quantity wearing different clothes. "247", "11110111", and "F7" are three spellings of the same number. Hex is just a shorthand so humans don't go cross-eyed reading bits.

**Deep dive (optional).** Each binary place doubles: 1,2,4,8,16,32,64,128. To go binary→hex, split into 4-bit groups and translate each: `1111 0111` → `F 7` → `F7`. This is why colors look like `#FF0000` (three bytes: red=FF, green=00, blue=00) and memory addresses are shown in hex.

**Build-task tie-in.** `bin(247)` → `'0b11110111'`, `hex(247)` → `'0xf7'`, and `0xF7` → `247`. Convert a few numbers both ways until the base-swapping feels ordinary.

**Check.** Learner can explain that binary and hex are just other bases for the same numbers, and that 2 hex digits make a byte.

## L3 — Text as numbers: ASCII and Unicode

**Concept.** Since the machine only has numbers, text is stored by agreeing on a **mapping** from characters to numbers. **ASCII** is an old, small map: 128 characters (English letters, digits, punctuation, control codes), so `A`=65, `a`=97, `0`=48, space=32. ASCII covers English but not é, 中, or 😀. **Unicode** is the giant modern map that gives a number (a "code point") to essentially every character in every writing system plus emoji. **UTF-8** is the most common way to actually store Unicode as bytes: it uses 1 byte for the old ASCII characters and 2–4 bytes for the rest.

**ELI5.** It's a codebook. Everyone agreed "65 means A." ASCII is a thin pocket codebook for English; Unicode is the enormous codebook for all languages; UTF-8 is the rule for writing those codebook numbers down as bytes.

**Deep dive (optional).** A common trap: one character is **not** always one byte. In UTF-8, `"a"` is 1 byte but `"😀"` is 4. That's why `len(text)` (characters) can differ from `len(text.encode("utf-8"))` (bytes), and why mismatched encodings turn text into garbled "mojibake."

**Build-task tie-in.** `ord("A")` → `65`, `chr(65)` → `"A"`. Then `len("café")` → `4` characters, but `len("café".encode("utf-8"))` → `5` bytes (the é takes two). Seeing those two numbers disagree is the whole lesson in one line.

**Under the hood.** When you open a file, the program must know the encoding (usually UTF-8 today) to turn bytes back into the right characters. There is no text "inside" the file — only bytes plus an agreed codebook.

**Check (mastery bar for m1).** Learner can explain that data is bits, a byte is 8 bits (256 values), and that text is characters mapped to numbers via a codebook like ASCII/Unicode — AND that one character isn't always one byte.
