# m5 — Data structures II: maps, trees, graphs

> Three structures that organize data by *relationship* rather than by position. Each is great at a different question.

## L1 — Hash maps: lookup by key, fast on average

**Concept.** A **hash map** (Python `dict`, JS `Map`/object) stores **key → value** pairs and answers "what's the value for this key?" almost instantly. The trick: it runs the key through a **hash function** that turns it into a number, and uses that number to decide which "bucket" (slot in an internal array) the pair goes in. Looking up a key hashes it again and goes straight to that bucket — so insert, lookup, and delete are **O(1) on average**. Worst case is O(n) when many keys collide into the same bucket, but good hash functions keep that rare.

**ELI5.** A hash map is a coat check. You hand over a coat (value) and get a numbered ticket (derived from a key). To get the coat back, the number sends the attendant straight to the right hook instead of searching every hook.

**Deep dive (optional).** When two keys hash to the same bucket (a **collision**), the map handles it (e.g. chaining items in that bucket). Keys must be **hashable** (stable and comparable) — that's why you can't use a list as a dict key in Python but can use a string or tuple. Honest nuance: a hash map is conceptually *unordered*, but CPython's `dict` has preserved **insertion order** since Python 3.7 — convenient, though you shouldn't lean on ordering as the *point* of a hash map.

**Build-task tie-in.** Compare finding a user by id in a list vs. a dict:
```python
by_id = {"u1": "Ada", "u2": "Alan"}
by_id["u2"]          # O(1) — straight to the value
# vs scanning a list of (id, name) pairs: O(n), checks each until it matches
```
On a big dataset the dict lookup stays instant while the list scan slows down with size.

**Check.** Learner can say a hash map gives average O(1) lookup by key via hashing, and that worst case degrades with collisions.

## L2 — Trees: hierarchy and sorted order

**Concept.** A **tree** organizes data in a hierarchy: one **root** node at the top, each node having child nodes below it, no cycles. It's the natural shape for anything nested — a file system (folders in folders), an org chart, the structure of a web page (the DOM). A special, important kind is the **binary search tree (BST)**: each node has up to two children, with smaller values left and larger right, which keeps data sorted and lets you find an item by repeatedly halving the search — **O(log n)** when the tree is **balanced**.

**ELI5.** A tree is a family tree flipped upside down: one ancestor at top, branching into descendants. A binary search tree is one where everyone's organized smallest-to-largest, so finding a name means "higher or lower?" over and over, cutting the possibilities in half each time.

**Deep dive (optional).** The O(log n) speed depends on the tree staying **balanced** (short and bushy). If you insert already-sorted data into a naive BST it degenerates into what's basically a linked list — back to O(n). Real libraries use self-balancing trees (red-black, AVL, B-trees) to prevent that; databases use B-trees for their indexes (m10).

**Build-task tie-in (standalone).** You usually reach for a `dict` instead of writing a BST, so sketch this on paper: a BST holding 1–7 with 4 at the root; finding 6 visits 4 → 6, just two steps out of seven. That halving is where O(log n) comes from.

**Check.** Learner can say a tree is a hierarchy with a root and children, and that a balanced search tree gives O(log n) lookup by halving.

## L3 — Graphs: things and the connections between them

**Concept.** A **graph** is the most general of the three: a set of **nodes** (vertices) connected by **edges**. Edges can be one-way (**directed**) or two-way (**undirected**), and can carry weights (a distance, a cost). Graphs model *relationships*: friendships in a social network, cities joined by roads, web pages linked to each other, tasks that depend on other tasks. A tree, in fact, is just a special graph (connected, no cycles, one root).

**ELI5.** A graph is a map of dots joined by lines. The dots are things (people, places), the lines are how they're connected (friends, roads). Questions like "can I get from A to B?" or "who are my friends-of-friends?" are graph questions.

**Deep dive (optional).** Classic graph problems: shortest path (GPS routing), reachability (can these computers talk?), ordering with dependencies (what to build first). Graphs are stored as an **adjacency list** (each node keeps a list of its neighbors — compact for sparse graphs) or an **adjacency matrix** (a grid of who-connects-to-whom). Exploring them uses breadth-first or depth-first search.

**Build-task tie-in.** A tiny graph as a dict of neighbor lists:
```python
friends = {"Ada": ["Alan", "Grace"], "Alan": ["Ada"], "Grace": ["Ada"]}
friends["Ada"]    # ['Alan', 'Grace'] — Ada's direct connections
```
From here "friends of friends" means following edges outward — the essence of graph traversal.

**Choosing between them.** Hash map → *"look something up fast by its key."* Tree → *"keep a hierarchy, or sorted data I can search by halving."* Graph → *"model arbitrary relationships and move between connected things."*

**Check (mastery bar for m5).** Learner can match each structure to a problem it fits: map = fast key lookup, tree = hierarchy/sorted search, graph = networks/relationships — and knows hash-map O(1) is average, not guaranteed.
