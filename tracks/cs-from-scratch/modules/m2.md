# m2 — Memory & how programs hold data

## L1 — Variables as named places in memory

**Concept.** While a program runs, its working data lives in **memory (RAM)** — a long row of numbered byte-slots, each with an **address**. A **variable** is a human-friendly *name* for a place that holds a value. When you write `score = 10`, the program stores the value and lets you say `score` instead of "the thing at address 140732…". Memory is fast but temporary: it's cleared when the program ends (that's why we save to disk for anything we want to keep).

**ELI5.** RAM is a giant wall of numbered lockers. A variable is a sticky note with a name — `score` — stuck on one locker so you don't have to remember its number.

**Deep dive (optional).** Different value types take different amounts of space (a small integer vs. a long string), and languages differ in how much of this they expose. In low-level languages (C) you feel addresses directly; in high-level languages (Python, JS) the runtime hides them, but the lockers are still there.

**Build-task tie-in.** In Python, `x = 10; id(x)` prints a number that stands in for *where* that value lives. Reassign `x = 11` and the name now points at a different value. The name and the value it refers to are two separate things — the key idea for L3.

**Check.** Learner can say a variable is a named place in memory holding a value, and that memory is temporary.

## L2 — The stack vs the heap (mostly under the hood)

**Concept.** Programs use two main regions of memory. The **stack** holds the bookkeeping for function calls — each call gets a small frame with its local variables — and it grows and shrinks automatically as functions are called and return. It's fast, orderly (last-in, first-out), and small. The **heap** is a larger, more free-form pool for data whose size or lifetime isn't tied to a single function call — things you create and keep using after the function that made them returns.

**ELI5.** The stack is a neat pile of trays in a cafeteria: you add a tray when you start a task, take it off when you finish, always from the top. The heap is a big warehouse where you can store a crate anywhere and keep a claim ticket (a reference) to find it again later.

**Deep dive (optional).** Local variables and the chain of "who called whom" live on the stack; large or long-lived objects live on the heap. In C you manage heap memory by hand (`malloc`/`free`); in Python/Java/JS a **garbage collector** reclaims heap data you can no longer reach. Running the stack past its limit (usually via runaway recursion — see m7) causes a **stack overflow**.

**Build-task tie-in (standalone).** This split barely shows up in a small Python program — the runtime handles it for you — so treat this as a mental model, not something to code. The one place you'll *feel* it is deep recursion crashing with "maximum recursion depth exceeded," which is the stack filling up (we'll see exactly that in m7).

**Under the hood.** "Fast stack vs. slower, flexible heap" is a real tradeoff that languages make for you. High-level languages hide it; it never stops happening underneath.

**Check.** Learner can describe the stack as fast, automatic call bookkeeping and the heap as a flexible pool for longer-lived data — without thinking they're interchangeable.

## L3 — Pointers & references: the address, not the thing

**Concept.** Sometimes a variable holds the actual value (the number 10). Other times it holds a **reference** (also called a **pointer**): the *address* of where the real data lives, not the data itself. This matters because two names can reference the *same* underlying object. Change it through one name and the other name "sees" the change too, because they point at one thing.

**ELI5.** A reference is a home address written on a card, not the house itself. If you and I both have cards with the same address and I repaint that house, your card now leads to a repainted house — there was only ever one house.

**Deep dive (optional).** This is why `b = a` can behave in two ways. For a simple value, `b` gets its own copy. For a shared mutable object (a list), `b = a` copies the *reference*, so `a` and `b` are two names for one list — "aliasing." To get an independent copy you copy the contents, not the reference.

**Build-task tie-in.** Run this and watch:
```python
a = [1, 2, 3]
b = a            # b references the SAME list
b.append(4)
print(a)         # [1, 2, 3, 4]  — a changed too!
```
Both names point at one list. Compare with `b = a.copy()`, where appending to `b` leaves `a` alone. That surprise is the pointer/reference concept biting in real life.

**Under the hood.** A reference is literally a small value holding a memory address (from L1). "Pass by reference vs. value" bugs — editing a caller's data by accident — all come from this one idea.

**Check (mastery bar for m2).** Learner can say what a variable is in memory, and explain the difference between holding a value and holding a reference to a value (including why two names can change the same object).
