## L1 — What the OS actually does

**Concept.** The **operating system** (Windows, macOS, Linux, Android, iOS) is the program that sits between your apps and the hardware. Its jobs: share the **CPU** among programs (scheduling who runs when), hand out and protect **memory**, manage **files** on disk, talk to **devices** (keyboard, screen, network), and keep programs **isolated** from each other so one crashing or misbehaving app can't trample another's memory. It does this through the **kernel**, the privileged core, and offers apps clean **abstractions** — "a file," "a process" — instead of raw hardware.

**ELI5.** The OS is the building manager for your computer. Apps are tenants; the manager decides who gets the elevator (CPU) and when, assigns rooms (memory), keeps tenants out of each other's apartments, and handles the plumbing and wiring (devices) so tenants don't have to.

**Deep dive (optional).** Apps don't touch hardware directly; they ask the OS via **system calls** ("open this file," "send these bytes"). The CPU runs in two modes — restricted **user mode** for apps, privileged **kernel mode** for the OS — so a buggy or hostile app can't directly reach hardware or other apps' memory. That boundary is the foundation of system security.

**Build-task tie-in.** Every time your code does `open("notes.txt")` or `print(...)`, it's really asking the OS to do the real work. The OS is the invisible layer under even a one-line program.

**Check.** Learner can list a couple of OS jobs (sharing the CPU, managing memory/files, isolating programs) and say the kernel is its core.

## L2 — Processes vs threads

**Concept.** A **process** is a running program with its *own* private, isolated memory. Two processes can't see each other's memory by default — that's the isolation from L1. A **thread** is a unit of execution *inside* a process; one process can have several threads, and crucially **threads in the same process share that process's memory**. So: processes = strong isolation, heavier to create; threads = lightweight, fast to switch between, but they share data (which is powerful and dangerous).

**ELI5.** A process is a house with its own locked doors. Threads are the people living in one house — they share the kitchen and fridge (memory). Different houses (processes) can't raid each other's fridges; housemates (threads) can, which is handy until two of them grab the same thing at once.

**Deep dive (optional).** Because threads share memory, two of them touching the same data at the same time can corrupt it — a **race condition** — so you need **synchronization** (locks) to take turns. Honest, implementation-specific aside: standard CPython has long used a **Global Interpreter Lock (GIL)** that keeps threads from running Python bytecode truly simultaneously, so CPU-heavy Python work is often parallelized with multiple *processes* instead of threads. (This is a CPython detail, not a rule of all languages, and it's an area of active change.)

**Build-task tie-in (standalone).** This is mostly conceptual for a beginner, but you can *see* it: Python's `threading` lets two threads print interleaved output (they share the process), while `multiprocessing` spins up separate processes with separate memory. Watching interleaved thread output makes "shared memory, taking turns" concrete.

**Check.** Learner can state that processes have isolated memory while threads within a process share memory, and that sharing invites race conditions.

## L3 — Concurrency vs parallelism (concept level)

**Concept.** These sound the same but aren't. **Concurrency** is *structuring* a program to juggle many tasks that are all "in progress" — making progress on each by switching between them, even on a single CPU core (the OS time-slices, giving each a sliver of CPU so fast it looks simultaneous). **Parallelism** is *actually* doing multiple things at the same instant, which needs multiple cores. Concurrency is about dealing with many things at once; parallelism is about doing many things at once. You can have concurrency without parallelism (one core, rapid switching) and parallelism is one way to execute concurrent work.

**ELI5.** Concurrency: one cook juggling several dishes, stirring one, then checking the oven, then chopping — all "going" but one pair of hands. Parallelism: several cooks each on their own dish at the same time. One is clever time-management; the other is more hands.

**Deep dive (optional).** The OS **scheduler** creates the illusion of concurrency by **context switching** — saving one task's state and loading another's, thousands of times a second. True parallelism arrived for everyday computers with **multi-core** CPUs. This is also why concurrency is hard: interleaving and shared data (L2) make bugs that only appear under certain timings.

**Build-task tie-in (standalone).** Think of a web server handling 100 users on a 4-core machine: it's *concurrent* (100 requests in flight) but only ever *parallel* 4-at-a-time (4 cores). Holding that picture is the whole lesson — no code required.

**Under the hood.** "My computer runs many apps at once" on a few cores is mostly concurrency (fast switching), with real parallelism only up to the number of cores.

**Check (mastery bar for m8).** Learner can explain process vs. thread (isolated vs. shared memory) AND concurrency vs. parallelism (juggling by switching vs. truly simultaneous), with an example of each.
