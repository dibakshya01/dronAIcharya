# m7 — Recursion

## L1 — Base case and recursive case

**Concept.** **Recursion** is when a function solves a problem by calling *itself* on a smaller version of the same problem. Every correct recursion has two parts: a **base case** — the smallest input where the answer is known outright and no further call is made — and a **recursive case** — which does a little work and calls itself on something *closer to the base case*. Miss the base case (or fail to shrink toward it) and the function calls itself forever.

**ELI5.** It's a set of nesting dolls. To count them you open one (do a bit of work) and count the dolls inside (the same task, smaller). The base case is the tiny solid doll with nothing inside — that's where you stop.

**Deep dive (optional).** The recursive case must *reduce* the problem each time, or you never reach the base case. "Reduce" usually means a smaller number, a shorter list, or a subtree. Recursion and loops are equally powerful — anything you can do with one you can do with the other — but some problems are far more natural one way.

**Build-task tie-in.** Factorial, the classic:
```python
def fact(n):
    if n == 0:        # base case: 0! is 1, stop
        return 1
    return n * fact(n - 1)   # recursive case: shrink toward 0

fact(5)   # 5*4*3*2*1 = 120
```
`fact(5)` calls `fact(4)` calls … `fact(0)` which returns `1`, and the answers multiply back up.

**Check.** Learner can name the base case and recursive case and say the recursive case must move toward the base case.

## L2 — The call stack and stack overflow

**Concept.** Recursion runs on the **call stack** from m2. Each call pushes a new frame holding that call's own `n` and a note of where to return. `fact(5)` stacks up 6 frames (`fact(5)` … `fact(0)`); when `fact(0)` returns, the frames **pop** one at a time, each multiplying in its value on the way out. The stack is finite, so if the recursion goes too deep — or never hits its base case — the stack fills and the program crashes with a **stack overflow** (in Python: "maximum recursion depth exceeded").

**ELI5.** Each recursive call is a sticky note you slap on top of a pile: "I'm waiting on the answer to the smaller problem." You can only answer the top note once the one above it is done, so the pile unwinds top-down. Pile too many notes and the desk overflows.

**Deep dive (optional).** This is the concrete payoff of m2's stack. Python caps recursion depth (around 1000 by default) precisely to turn a runaway recursion into a clean error instead of crashing the whole process. Some languages optimize certain recursions (**tail-call elimination**) so they reuse one frame; CPython deliberately does not, which is why very deep recursion in Python should be rewritten as a loop.

**Build-task tie-in.** Call `fact(-1)` (or any function with no reachable base case) and watch it recurse until Python raises `RecursionError`. That error *is* the stack filling up — exactly the stack-overflow idea made visible.

**Under the hood.** Each frame costs memory. That's why "just make it recursive" isn't free: depth n means n frames alive at once (O(n) space), even when a loop would use O(1).

**Check.** Learner can explain that each recursive call adds a stack frame and that too-deep (or base-case-less) recursion overflows the stack.

## L3 — When recursion helps (and when a loop is better)

**Concept.** Recursion shines when the *data* or the *problem* is itself recursive: trees and nested structures (folders within folders, the DOM, JSON), and **divide-and-conquer** algorithms that split a problem into smaller same-shaped pieces (merge sort, binary search, exploring a maze). For flat, linear work — summing a list, counting to a million — a plain loop is usually clearer, faster, and safe from stack overflow.

**ELI5.** Use recursion when the thing you're working on branches like a tree; use a loop when you're just marching down a straight line.

**Deep dive (optional).** A recursive solution often reads closer to the problem's definition ("a folder's size is its files plus the size of each subfolder") which makes it easier to get right. The costs are stack memory and, sometimes, repeated work. The judgment call: reach for recursion when it makes a tree-shaped problem obvious, and for a loop when recursion would just be a fragile way to count.

**Build-task tie-in.** Summing a nested list is natural recursively — recurse into sublists, add up numbers:
```python
def deep_sum(x):
    if isinstance(x, list):
        return sum(deep_sum(item) for item in x)   # recurse into each
    return x                                        # base case: a number

deep_sum([1, [2, [3, 4]], 5])   # 15
```
Try writing that with only loops and you'll feel why the tree shape wants recursion.

**Check (mastery bar for m7).** Learner can name the two parts every recursion needs, explain the call stack's role (and overflow), and give one problem where recursion fits better than a loop and one where a loop is better.
