## L1 — Source code → machine code: compiling vs interpreting

**Concept.** You write **source code** — text a human can read (`print("hi")`). The CPU can't run that directly; it only runs **machine code** (raw numeric instructions). Two main ways bridge the gap. A **compiler** translates the whole program to machine code *ahead of time*, producing a file you then run (C, Rust, Go). An **interpreter** is a program that reads your source and carries it out *as it goes*, line by line, each time you run it (classic Python, JavaScript, Ruby).

**ELI5.** Compiling is translating a whole book into another language and handing over the finished translation. Interpreting is having a live translator stand next to you and translate each sentence out loud as you speak.

**Deep dive (optional).** Tradeoffs: compiled programs usually run faster and ship as a standalone binary, but need a build step and are tied to one kind of machine. Interpreted programs are more portable and skip the build step, but run slower. Real languages blur this: Java and C# compile to **bytecode** run by a virtual machine; modern JavaScript engines compile to bytecode and then use **JIT** (just-in-time) compilation to speed hot code up. Python compiles your source to bytecode too, but standard CPython mainly *interprets* that bytecode — JIT shows up in other implementations (like PyPy) and as an experimental, opt-in feature in very recent CPython. So "compiled vs. interpreted" is a spectrum, not two boxes.

**Build-task tie-in.** Running `python hello.py` *feels* instant, but CPython quietly compiles your source to bytecode (the `.pyc` files in `__pycache__`) and then runs that. "Interpreted" doesn't mean "no compiling happens" — it means the translating happens as part of running.

**Check.** Learner can explain compiling (translate all up front) vs. interpreting (translate while running), and that the CPU ultimately runs machine code either way.

## L2 — What machine code is

**Concept.** **Machine code** is a sequence of very simple numeric instructions the CPU understands directly: "load the number at this address into a register," "add these two registers," "if this is zero, jump to that instruction," "store this result." Each instruction is tiny; a real program is millions of them. Machine code is specific to a CPU's **instruction set architecture** (ISA) — x86-64 (most laptops/desktops) and ARM (phones, Apple Silicon) speak different machine codes, which is why a program built for one may not run on the other without recompiling.

**ELI5.** Machine code is the computer's native muscle memory: not "sort these names," but thousands of baby steps like "pick up box, move left, compare, put down." The CPU is incredibly fast at incredibly small steps.

**Deep dive (optional).** **Assembly** is a human-readable nickname for machine code (`ADD`, `MOV`, `JMP`) — one assembly line usually maps to one machine instruction. High-level code like `total = a + b` becomes several machine instructions: load `a`, load `b`, add, store `total`.

**Build-task tie-in (standalone).** You won't hand-write machine code here — that's the point of high-level languages. If you're curious, Python's `dis` module (`import dis; dis.dis(f)`) shows the *bytecode* a function compiles to, which is the same idea one level up from raw machine code: small, explicit steps.

**Check.** Learner can say machine code is simple numeric instructions the CPU runs directly, and that it's specific to a CPU architecture.

## L3 — What a CPU does in a loop (fetch–decode–execute)

**Concept.** A CPU runs by repeating one tiny loop, billions of times a second: **fetch** the next instruction from memory (it keeps a "program counter" pointing at where it's up to), **decode** what that instruction means, **execute** it (do the add, the compare, the jump, the store), then advance and repeat. That's it. Everything — your game, browser, this lesson — is this loop grinding through machine instructions.

**ELI5.** Imagine a worker with a to-do list and a finger on the current line: read the line, understand it, do it, move the finger down, repeat — unbelievably fast and never bored.

**Deep dive (optional).** The CPU uses **registers** (a handful of ultra-fast slots) for the values it's working on right now, and a **clock** that paces the steps (gigahertz = billions of ticks per second). Real CPUs do many instructions at once (pipelining), guess which branch comes next, and use **caches** to avoid waiting on slow main memory — optimizations on top of the same fetch–decode–execute idea.

**Build-task tie-in (standalone).** This loop is below where your code can see, so treat it as a model. The payoff: it's why a loop that does fewer steps runs faster (straight into m6/Big-O), and why "the computer is just following instructions, one after another" is literally true.

**Under the hood.** Jumps are how `if`/`while`/function calls work at this level: the program counter is set to a different instruction instead of just the next one.

**Check (mastery bar for m3).** Learner can trace the path source → (compiled or interpreted) → machine code, AND explain that the CPU repeats fetch–decode–execute to run it.
