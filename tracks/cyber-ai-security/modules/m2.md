# m2 — How the web works for security

> Teach one lesson at a time, at the learner's level, then check. The goal here is a correct mental model of what protects what — not a networking deep-dive.

## L1 — HTTP: the request→response shape, and that it's stateless

**Concept.** The web runs on **HTTP**: your browser sends a **request** (a method like `GET` or `POST`, a URL, some headers, maybe a body), and the server sends back a **response** (a status code like `200` or `403`, headers, and the content). That's the whole conversation, one round trip at a time. Crucially, HTTP is **stateless**: the server doesn't remember you between requests on its own. Each request arrives as if it's the first the server has ever seen.

**ELI5.** It's like mailing a postcard and getting one back. The post office doesn't remember your last postcard — if you want continuity, *you* have to write "this is me again, remember yesterday?" on every card.

**Deep dive (optional).** Because the server trusts nothing by default, *everything the client sends is attacker-controllable* — URL, headers, cookies, body, all of it. "The client will only send valid data" is the assumption behind a huge share of web vulnerabilities. Validate on the server; the client is a suggestion, not a guarantee.

**Build-task tie-in.** Open your app's network tab in the browser and watch one action turn into a request and a response. Notice the status code and that the request is just text you could have typed yourself. That "I could type this myself" feeling is the attacker's starting point.

**Check.** Learner can describe HTTP as request→response and say that the server doesn't remember them between requests without help.

## L2 — Cookies & sessions: how a server remembers you

**Concept.** Since HTTP forgets, apps use a **session** to stay logged in. After you sign in, the server creates a session and hands the browser a **cookie** — a small token the browser automatically attaches to every later request. The server sees the cookie and says "ah, this is the user who logged in." The cookie is effectively your temporary key to the account for as long as the session lasts.

**ELI5.** The nightclub stamps your hand when you pay at the door (login). After that the stamp (cookie) gets you back in without paying again — but anyone who copies your stamp gets in as you.

**Deep dive (optional).** If an attacker steals the session cookie (via a cross-site scripting bug, an insecure network, or a leak), they are logged in as you without ever knowing your password — that's **session hijacking**. Defenses: mark cookies `HttpOnly` (JavaScript can't read them, blunting theft via XSS), `Secure` (only sent over HTTPS), and `SameSite` (not sent on sketchy cross-site requests); expire sessions; and rotate the session token on login.

**Build-task tie-in.** Find where your app sets its session/login cookie. Check whether it's marked `HttpOnly` and `Secure`. If a framework handles it, confirm the setting rather than assuming the default is safe.

**Check.** Learner can explain that a cookie/session is how the server remembers a logged-in user, and that stealing it can mean logging in as that user without the password.

## L3 — TLS/HTTPS: what it protects, and the big thing it doesn't

**Concept.** **HTTPS** is HTTP wrapped in **TLS** encryption. It does two real things: it keeps the data **confidential in transit** (someone sniffing the network sees scrambled bytes, not your password), and it protects **integrity in transit** (the data can't be silently altered on the way), plus it verifies you're talking to the server that owns that domain's certificate. That's genuinely important — but it's *only about the pipe between browser and server*.

**ELI5.** HTTPS is an armored truck between your house and the bank. It stops robbers on the road. It says nothing about whether the "bank" at the other end is a real bank or a convincing fake — and nothing about what happens to your money once it's inside.

**Deep dive (optional).** The dangerous misconception: **"the padlock / HTTPS means the site is safe and trustworthy."** It does not. Phishing sites get valid certificates for free in minutes. HTTPS does *not* mean the site is honest, the server is free of bugs, your data is safe once stored, or the input you send is validated. It protects transit, full stop. A perfectly phishing-y site over HTTPS is still phishing.

**Build-task tie-in.** Confirm your app is served over HTTPS (it should be, in production). Then write one line in your threat model noting what HTTPS does *not* cover for you — stored data, access control, input validation — because those are the next modules.

**Check (mastery bar for m2).** Learner can state that HTTPS protects confidentiality and integrity *in transit* and verifies the domain, AND explain why "it's HTTPS" does not mean a site is safe, honest, or bug-free.
