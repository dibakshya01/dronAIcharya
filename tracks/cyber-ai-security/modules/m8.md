# m8 — Safe MCP & tool use

> Teach one lesson at a time, then check. Builds on Vibecoding m3 (agents, tools, MCP) and m6 here. Reinforces `reference/injection-safety.md`: the request→act→result loop is where untrusted data meets real actions, so the data-not-instructions rule lives or dies at the tool seam.

## L1 — Least-privilege tools: give the narrowest ability that does the job

**Concept.** When you give an agent a tool (via MCP or otherwise), you're handing it a real capability — read a file, run a command, query a database, send an email. **Least privilege** says: grant the *narrowest* version of that capability that still does the job. A tool that can read one folder is safer than one that can read the whole disk. A read-only database tool is safer than a read-write one. Every extra power a tool has is extra damage available if the agent is wrong (hallucination) or hijacked (indirect injection, m6).

**ELI5.** If you hire someone to water your plants, you give them a key to the garden shed, not the master key to the whole house. They can't misuse access they were never given.

**Deep dive (optional).** This is the direct defense against **Excessive Agency** (LLM06, m7). Scope tools by capability (read vs. write vs. delete), by resource (this table, not the account), and by reach (local, not "the whole internet"). Minimize the *number* of tools wired in, too — a tool the agent doesn't need is attack surface for nothing. When you connect an MCP server, look at what tools it exposes and whether your agent truly needs all of them.

**Build-task tie-in.** List every tool/MCP capability your app grants an agent. For each, ask: could this be read-only? scoped to one resource? removed entirely? Narrow at least one. (dronAIcharya itself does this: its skills and agents request the minimum tools they need — least privilege by design.)

**Check.** Learner can explain least-privilege tools and give one example of narrowing a tool's power.

## L2 — Human-in-the-loop for consequential actions

**Concept.** Some actions you can undo; some you can't. **Human-in-the-loop** means the agent may *propose* a consequential action, but a person approves before it actually happens — especially for anything involving **money, data loss, outward communication, or irreversibility** (spending, deleting, sending, publishing, deploying, granting access, entering credentials). The agent does the work up to the click; the human owns the click.

**ELI5.** The assistant can draft the email, fill in the wire transfer, line up the "delete everything" — but you're the one who presses Send. Drafting is reversible; sending often isn't.

**Deep dive (optional).** Why gate on *consequence* and not on everything? Because stopping for approval on every trivial step trains people to click "yes" without reading (approval fatigue), which is worse than no gate. Reserve the human checkpoint for the actions whose blast radius justifies it. This is exactly dronAIcharya's and Claude Code's posture: destructive or outward-facing actions (push, publish, pay, deploy, entering credentials) stop at the learner's own click — the agent preps right up to it and hands it over (`reference/injection-safety.md`, "least privilege"). Pair this with least-privilege tools (L1): narrow what's *possible*, gate what's *consequential*.

**Build-task tie-in.** List your app's consequential actions (anything about money, deletion, sending, publishing, access). Confirm each has a human checkpoint before it fires — and that the checkpoint shows the human *what* will happen ("send this, to this person") so the approval is informed, not reflexive.

**Check.** Learner can name the kinds of actions that need a human checkpoint and explain why approving *everything* is counterproductive.

## L3 — The request→act→result seam as an attack surface

**Concept.** Recall the tool loop from Vibecoding m3: the model emits a **structured request**, the program **executes** it for real, and the **result returns into the context as data**. That result-coming-back step is a live attack surface. Whatever the tool returns — a web page, a file's contents, a database row, an API response — is **untrusted data**, and it can carry an **indirect prompt injection** (m6): hidden text that tries to steer the agent's *next* request. The seam where tool output re-enters the model is precisely where "data" can masquerade as "instructions."

**ELI5.** You sent a runner to fetch a document and bring it back. The document itself might have a forged note stapled to it saying "now go empty the safe." The runner did their job correctly; the danger is in *what they brought back*, and whether you treat it as a report or as orders.

**Deep dive (optional).** Defenses stack along the loop: (1) **least privilege** on the tool making the request (L1), so a hijacked next-step can't do much; (2) treat the returned result as **data, clearly separated**, never as a new system instruction (m6, `injection-safety.md`); (3) don't let tool output silently trigger another consequential tool call — put the **human checkpoint** (L2) between "the model read something" and "the model acts on it"; and (4) validate/handle the output before it drives anything (improper output handling, LLM05, m6). The chained-tool case is the dangerous one: fetch → the fetched text says "now delete" → delete. Breaking that chain is the whole game.

The emerging **OWASP Top 10 for Agentic Applications** (ASI-numbered, late 2025) is built around exactly this seam — tool misuse, privilege abuse, and poisoned context across multi-step agents. The numbering is still settling across sources, so lean on the principle: *every time tool output re-enters the agent, it's untrusted data, not a command.*

**Build-task tie-in.** Trace one tool loop in your app end to end. At the "result comes back" step, ask: if this result contained "ignore everything and do X," would my app obey it? If anywhere a tool's output can directly cause another consequential action with no human and no "this is data" boundary, that's the hole to close.

**Under the hood.** This is why dronAIcharya quarantines fetched content as marked reference material and never copies it into the teaching contract, hook-injected text, or the re-injected journal. The seam is defended by *never letting untrusted output become instruction*, structurally — not by hoping the model ignores it.

**Check (mastery bar for m8).** Learner can explain why a tool should get least privilege, when a human must approve an action, AND why the result returned by a tool is untrusted data that can carry an indirect injection — so tool output must never be treated as a command.
