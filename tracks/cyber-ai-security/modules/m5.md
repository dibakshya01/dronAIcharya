# m5 — OWASP Top 10, part 2: auth, misconfig, supply chain & the rest

> Teach one lesson at a time, then check. This module covers the remaining 2025 categories. Keep it concrete — tie each to the learner's own app, skim the ones that don't apply.

## L1 — Authentication Failures (A07)

**Concept.** **Authentication** is proving *who you are* (login); **authentication failures** are the ways that proof gets bypassed or weakened. The usual suspects: passwords with no strength requirements, no lockout or rate limiting (so attackers can guess endlessly), no multi-factor option, storing passwords in plain text or weakly hashed, and sessions that don't expire. (Authentication = who you are; **authorization**, from m4, = what you're allowed to do. Different jobs, both required.)

**ELI5.** Authentication is the bouncer checking your ID at the door. Weak authentication is a bouncer who accepts "trust me, I'm 21," lets you keep guessing the password a million times, and never asks for a second proof.

**Deep dive (optional).** Good baseline: let users pick long passphrases (length beats forced symbols), hash with a slow, salted algorithm built for passwords (bcrypt/argon2 — never plain `sha256`, never plaintext), rate-limit and lock out after repeated failures, offer MFA, and expire/rotate sessions. Don't roll your own auth if a vetted library or provider will do it — this is a place to stand on proven tools.

**Build-task tie-in.** If your app has login, check three things: are passwords hashed with a password-specific algorithm, is there any limit on guesses, and do sessions expire? If a provider handles auth for you, confirm those are on rather than assuming.

**Check.** Learner can name two authentication failures (e.g. unlimited guessing, plaintext passwords) and one fix each.

## L2 — Security Misconfiguration (A02)

**Concept.** **Security misconfiguration** jumped to #2 in 2025: the code may be fine, but something is *set up* insecurely. Default admin passwords left unchanged, debug mode on in production, detailed error messages exposed to users, cloud storage buckets left public, unnecessary features or ports open, missing security headers. It's the most common real-world foothold because it needs no clever exploit — just something left at an unsafe default.

**ELI5.** You bought a great safe, then left it on the "0-0-0" factory combination and propped the door open "just while we move in." The safe is fine; the setup is the problem.

**Deep dive (optional).** Defenses: change every default credential; turn off debug/verbose errors in production (they leak stack traces, paths, versions — gifts to an attacker); lock down storage to private by default; remove sample apps and unused features; set standard security headers. Treat configuration as code you review, because "it worked in dev with debug on" is how secrets end up in error pages.

**Build-task tie-in.** Check your app's production config: is debug off, are error pages generic (not full stack traces), is any storage bucket private, and did you change every default password? One public bucket or one debug page is a real finding.

**Check.** Learner can describe misconfiguration as an insecure *setup* (not a code bug) and give one example with its fix.

## L3 — Software Supply Chain Failures (A03)

**Concept.** Your app isn't just your code — it's your code plus every library, package, and base image you pulled in, and the tools that built and shipped it. **Software supply chain failures** (new as a top-3 category in 2025, broadening the old "vulnerable and outdated components") are when a weakness rides in through those dependencies: a library with a known vulnerability, an outdated package, or a malicious package that slipped into your build. You inherit the security of everything you install.

**ELI5.** You can cook a perfectly clean meal, but if one of the pre-packaged ingredients you bought was contaminated at the factory, your meal is contaminated too. You have to trust (and check) your ingredients, not just your cooking.

**Deep dive (optional).** Defenses: keep a **lockfile** so builds are reproducible; run a **dependency / software composition analysis (SCA)** scanner (GitHub Dependabot and similar flag known-vulnerable versions); update promptly when advisories land; pin versions and be wary of typosquatted package names (`reqeusts` vs `requests`); and minimize dependencies you don't need. Know what's in your app — a dependency you forgot is a dependency you can't patch.

**Build-task tie-in.** Look at your project's dependency manifest and lockfile. Turn on automated dependency alerts in your repo if available, and check whether anything is flagged as vulnerable. Fewer, current, well-known dependencies beat a pile of stale ones.

**Check.** Learner can explain that dependencies are part of their attack surface and name one defense (lockfile, SCA/alerts, prompt updates, minimize deps).

## L4 — The rest at a glance

**Concept.** The remaining 2025 categories, briefly — enough to recognize and look up:
- **A04 Cryptographic Failures** — sensitive data not protected properly: weak or missing encryption, home-grown crypto, plaintext secrets. *Fix:* use standard, vetted algorithms and libraries; encrypt sensitive data at rest and in transit; never invent your own crypto.
- **A06 Insecure Design** — the *design* is flawed, not just the code (e.g. a password-reset flow with no identity check). *Fix:* threat-model early (m1); some risks can't be patched later, only designed out.
- **A08 Software or Data Integrity Failures** — trusting code, updates, or data whose integrity you never verified (unsigned updates, untrusted CI plugins, insecure deserialization). *Fix:* verify signatures/checksums; trust sources deliberately.
- **A09 Security Logging and Alerting Failures** — not recording security-relevant events, or recording but never *alerting*, so breaches go unnoticed for months. *Fix:* log auth and access events, monitor them, and alert on the suspicious ones.
- **A10 Mishandling of Exceptional Conditions** — errors and edge cases handled badly: failing *open* instead of closed, leaking details in errors, crashing on unexpected input. *Fix:* fail safely (deny on error), handle edge cases, keep error messages generic.

**ELI5.** The headline risks are the front door; these are the side windows, the alarm you never wired up, and the "what happens when something unexpected walks in." Each matters; which ones matter *most* depends on your app.

**Build-task tie-in.** For each of the five, write one line in your threat model: does it apply to my app, and if so what's my one defense? Most small apps can address them in a sentence each; the point is to have *looked*.

**Under the hood.** "Fail closed, not open" is a recurring theme — when something goes wrong, the safe default is to *deny*, not to wave it through. That's the same deny-by-default instinct you'll formalize in m9.

**Check (mastery bar for m5).** Learner can name three more OWASP risks beyond injection and access control (e.g. authentication failures, misconfiguration, supply chain) and give one defense for each.
