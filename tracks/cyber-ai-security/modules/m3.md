# m3 — Secrets & key hygiene

> Teach one lesson at a time, then check. Never type, echo, or commit a real secret during these lessons — the learner handles their own keys. Reinforce `reference/injection-safety.md`: secrets never transit through the agent, hooks, or the journal.

## L1 — Why keys never go in code or repos

**Concept.** A **secret** is anything that proves "I'm allowed" — an API key, a database password, a token. The rule: secrets never live in your source code or your git repository. The reason isn't just "someone might see the file." It's that **git history is forever**: once a key is committed, deleting it in a later commit does *not* remove it — it's still sitting in the history, recoverable by anyone with the repo. Push that to a public GitHub and automated scanners find it in minutes.

**ELI5.** Writing your house key's cut-pattern into your diary doesn't become safe just because you cross it out on a later page. Anyone flipping back a few pages still has your key. Git is that diary, and it never really erases a page.

**Deep dive (optional).** A leaked key is worse than a leaked password: keys often have no second factor, work from anywhere, and may bill real money (cloud keys have funded large crypto-mining bills on stolen credentials). Public-repo keys are harvested by bots continuously; "it's a small project nobody will notice" is not a defense.

**Build-task tie-in.** Search your project for anything that looks like a key hard-coded in a file. If you find one, treat it as already compromised — we'll rotate it in L3, not just delete the line.

**Under the hood.** This is why dronAIcharya's `.gitignore` excludes `.env`, `*.key`, `*.pem`, and `.dronacharya/`, and why the guru never writes a key into the journal. The secret should only ever exist in places git can't reach.

**Check.** Learner can explain why committing a key is dangerous even if you delete it later (git history keeps it).

## L2 — `.env`, environment variables, and secret managers

**Concept.** So where *does* the secret go? Out of the code and into the **environment**. Locally, that's usually a `.env` file (key=value lines) that is **gitignored** — the code reads the value from the environment at runtime instead of containing it. In production, the same values are set as **environment variables** on the host, or stored in a **secret manager** (a service built to hold secrets with access control and audit logging). The code says "give me the value named `API_KEY`"; it never knows the value literally.

**ELI5.** Instead of taping the safe combination to the safe, you keep the combination in your head (the environment) and the safe just asks "what's the combo?" at opening time. The instructions on the safe never contain the combo.

**Deep dive (optional).** `.env` is fine for local dev but is still a plaintext file on disk — don't ship it, don't paste it in chat, don't commit it. A real secret manager (cloud KMS/secrets services) adds rotation, per-service access, and a log of who read what. Also keep an `.env.example` with the *names* but no values, so collaborators know what to set.

**Build-task tie-in.** Move any hard-coded secret into a gitignored `.env`, read it from the environment in code, and add a value-free `.env.example`. Confirm `.env` is in `.gitignore` *before* your next commit.

**Check.** Learner can describe keeping the secret in the environment (e.g. a gitignored `.env`) while the code only references its name.

## L3 — Least privilege, scoping, and rotation

**Concept.** Two habits make secrets survivable. **Least privilege / scoping:** a key should grant the *narrowest* access that does the job — read-only if you only read, one bucket not the whole account, a test key in test. **Rotation:** keys have a lifecycle; you replace them periodically, and *immediately* if one might have leaked. "Rotate" means issue a new key, update the environment, then revoke the old one — so a stolen key stops working.

**ELI5.** Give the dog-walker a key to the front door only, not the master key to every room (scoping). And if you ever lose a key, you change that lock rather than hoping nobody finds it (rotation).

**Deep dive (optional).** Blast radius is the point: when (not if) a scoped, rotatable key leaks, a read-only test key is a shrug and a full-access production key is an incident. Prefer short-lived tokens where the platform offers them. After any suspected leak, assume it's compromised — rotate first, investigate second.

**Build-task tie-in.** For each key your app uses, write one line: what can it do, and could it be narrower? If you found a committed key in L1, rotate it now (issue new, update `.env`, revoke old) rather than just deleting the line — the old one is still in history and must be made useless.

**Under the hood.** Least privilege isn't only for keys — it's the same principle behind least-privilege *tools* for AI agents (m8) and deny-by-default *backends* (m9). Give exactly the access needed, nothing spare.

**Check (mastery bar for m3).** Learner can explain why a committed key is dangerous AND name two mitigations (e.g. keep it in a gitignored environment, scope it to least privilege, rotate on leak).
