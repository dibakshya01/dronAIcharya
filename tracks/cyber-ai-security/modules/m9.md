# m9 — Deny-by-default backends

> Teach one lesson at a time, then check. L3 uses the optional purple-sparrow backend as a *live* example when it's connected; when it isn't, teach the same ideas conceptually. Surface purple-sparrow's own alpha "needs audit" caveat honestly — it's a teaching moment, not something to hide.

## L1 — Default-deny access policies

**Concept.** When you decide who can access what, you can start from "yes" or from "no." **Deny by default** means the system refuses everything unless a rule *explicitly* allows it — the opposite of allowing everything and trying to blocklist the bad cases. It's safer because the failure mode is *locked*, not *open*: if you forget to write a rule, the forgotten thing is denied (annoying but safe) rather than exposed (a breach). You grant access on purpose, one allow-rule at a time.

**ELI5.** A nightclub with a guest list (deny-by-default): if your name isn't on the list, you don't get in. The alternative — "everyone's welcome unless I've specifically banned you" — means the one troublemaker you forgot to ban walks right in. The guest list fails safe; the banned-list fails open.

**Deep dive (optional).** This is the same "fail closed, not open" instinct from m5's A10 and the least-privilege idea from m3 and m8, applied to data access. Allow-listing is more work up front (you have to name what's permitted) and far safer in practice, because the dangerous mistakes are *omissions*, and omissions should deny. "We'll lock it down later" tends to become a permanent open door.

**Build-task tie-in.** Look at how your backend decides access. Is the default "open unless blocked" or "closed unless allowed"? If anything is world-readable or world-writable by default, flip the question: what would it take to make the default *deny*, and allow only what's needed?

**Check.** Learner can explain deny-by-default and why failing closed is safer than failing open.

## L2 — Row-level security: authorization at the data layer

**Concept.** The most-dumped-on lesson from m4 (broken access control) was that hiding a button in the UI is not access control. **Row-level security (RLS)** is the proper fix: the rule "a user can only see their own rows" is enforced *at the database/data layer*, so even if a request slips past the UI and the application code, the data store itself refuses to return another user's rows. Authorization lives next to the data, not only on the screen.

**ELI5.** Instead of trusting the waiter to only bring you your own order, the kitchen itself refuses to plate anyone else's meal for you. Even if someone tricks the waiter, the kitchen won't cooperate.

**Deep dive (optional).** UI checks, API checks, and data-layer checks are *layers*, not substitutes — but the data layer is the backstop that holds when the others are bypassed (a forged request, a bug in the app code, an over-privileged agent, m8). RLS policies typically key off the authenticated user's identity: `allow read where row.owner == current_user`. This is also the backstop that protects LLM apps from sensitive-data disclosure (m7): if the model's retrieval tool can only ever read the current user's rows, a prompt injection can't make it fetch someone else's.

**Build-task tie-in.** For your most sensitive table, write the ownership rule in words ("a row is visible only to the user who created it") and check whether that rule is enforced at the data layer — not just by a filter in your application code that a bug could skip.

**Check.** Learner can explain row-level security and why enforcing authorization at the data layer backs up (and outlasts) UI and app-code checks.

## L3 — A live example: purple-sparrow's policy engine + `run_advisor`

**Concept.** dronAIcharya can optionally connect (over MCP) to **purple-sparrow**, an agent-native backend whose access control is a **deny-by-default policy engine** — exactly the idea from L1. When it's connected, you learn these concepts against a *real* backend instead of mock data: you `create_table`, write an access **policy** with `create_policy` (allow-rules on top of a default-deny base), `insert_record` / `query_records`, and then run `run_advisor` — a built-in **security advisor** that inspects your setup and surfaces findings (e.g. a table left too open, a policy that's broader than it should be) for you to fix live. Seeing the advisor flag a real weakness, and fixing it, is the lesson.

**ELI5.** It's a practice backend with a built-in safety inspector. You build the rooms and locks, then the inspector walks through and says "this door has no lock yet" — and you fix it while someone explains why it mattered.

**The honest caveat (surfaced, not hidden).** purple-sparrow describes *itself* as early-stage — its README says "beta," its badge says "alpha," and it explicitly states that its **policy engine needs an independent security audit before holding regulated data.** So: it's excellent for *learning* deny-by-default and row-level policies against a real engine, and you should **never put real or regulated data (real users' PII, payment data, health data) into it** while it carries that caveat. dronAIcharya surfaces this honestly because that's the security mindset in action — a tool telling you its own limits is doing exactly the right thing, and believing it is on you. (This connects straight back to m5's supply-chain lesson: you inherit the maturity of what you depend on, so you read the caveats.)

**Build-task tie-in.** If purple-sparrow is connected, model one of your app's tables in it, write a deny-by-default policy so a user sees only their own rows, then run `run_advisor` and fix whatever it flags — with test data only, never real data. If it's *not* connected, do the same exercise conceptually: write the default-deny policy and the per-user ownership rule for your real backend in plain language, and check your backend enforces them.

**Under the hood.** Notice the layering the whole track has been building toward: least-privilege keys (m3), least-privilege tools (m8), deny-by-default data policies (here), and a human on consequential actions (m8). Each is the same instinct — grant the minimum, deny by default, verify at the lowest layer — applied at a different spot.

**Check (mastery bar for m9).** Learner can explain default-deny AND why authorization belongs at the data layer (row-level security), not only the UI — and can state, honestly, why an alpha backend like purple-sparrow is fine for learning but not for real/regulated data.
