# m4 — OWASP Top 10, part 1: injection & broken access control

> Teach one lesson at a time, then check. Examples are vulnerable *patterns* shown so the learner can spot and fix them in their own code — never working exploits against real systems.

## L1 — What the OWASP Top 10 is

**Concept.** The **OWASP Top 10** is a widely used, free list of the most common and impactful web application security risks, published by the Open Worldwide Application Security Project (OWASP) and refreshed every few years from real-world data. It's not a law or a certification — it's a shared checklist so builders can cover the risks that actually show up most. The current edition is **OWASP Top 10:2025**, which replaced the long-standing 2021 list.

**ELI5.** It's the "top 10 ways houses actually get broken into" list, compiled from real break-ins — so instead of worrying about everything, you fix the doors and windows that burglars really use.

**Deep dive (optional).** The 2025 top three are **A01 Broken Access Control**, **A02 Security Misconfiguration**, and **A03 Software Supply Chain Failures**; **A05** is **Injection**. If you see an older "A06: Vulnerable and Outdated Components" elsewhere, that's the 2021 edition — in 2025 it was broadened and renamed into the supply-chain category. We cover A01 and A05 in this module and the rest in m5.

**Build-task tie-in.** Keep your m1 threat model open. As we walk the list, mark which items could actually hit your app — most small apps are genuinely exposed to access control, injection, misconfig, and supply chain, and can skim the rest.

**Check.** Learner can say the OWASP Top 10 is a data-driven list of the most common web risks, and that the current edition is 2025.

## L2 — Injection (A05), including SQL injection

**Concept.** **Injection** happens when untrusted input is mixed into a command or query so that the input is treated as *code* instead of *data*. The classic is **SQL injection**: a login form builds a database query by gluing the user's text directly into the query string. A normal user types a name; an attacker types text that *changes the query itself*, making the database do something it shouldn't. The root cause is always the same — data and code got mixed in the same string.

**ELI5.** Imagine a form letter where you paste the customer's name into "Dear ___." If someone's "name" is actually a whole new paragraph of instructions, and you paste it in and mail it, you just sent *their* instructions over your signature. Injection is pasting attacker text into a place where it gets obeyed.

**Deep dive (optional).** The fix is **parameterized queries** (also called prepared statements): you write the query with placeholders (`WHERE name = ?`) and hand the user's value *separately*, so the database always treats it as data, never as query structure. The same idea generalizes: never build commands by string-concatenating untrusted input — not for SQL, OS commands, or anything else. Input validation and escaping help as backup layers, but *separating code from data* is the real fix. (You'll meet this exact idea again in m6: prompt injection is "injection" for LLMs — untrusted text landing where instructions are read.)

**Build-task tie-in.** Find any place your app talks to a database or runs a command with user input. Confirm it uses parameters/placeholders, not string concatenation. If AI generated that code, this is a prime thing to check — generated data access sometimes concatenates.

**Under the hood.** "I'll just filter out bad characters" is fragile — attackers find encodings and cases you didn't list. Allow-listing what's valid and parameterizing beats trying to blocklist every bad input.

**Check.** Learner can explain injection as "untrusted input treated as code," name SQL injection as an example, and state the fix (parameterized queries / keep data separate from code).

## L3 — Broken Access Control (A01)

**Concept.** **Broken access control** is the #1 risk on the 2025 list: the app lets someone do or see something they shouldn't, because the "are you allowed to do this?" check is missing, weak, or only enforced in the UI. The most common flavor is changing an identifier in a request — `/invoice/123` to `/invoice/124` — and getting *someone else's* data because the server never checked that the invoice belongs to you (this is called an **IDOR**, insecure direct object reference).

**ELI5.** The hotel gives you a key to room 214, but every door opens with any key and the only thing stopping you from entering room 215 is a polite sign. Access control done right means each lock actually checks *your* key, not a sign asking nicely.

**Deep dive (optional).** Key principles: **enforce authorization on the server for every request**, not just by hiding buttons in the UI (the attacker doesn't use your UI); **deny by default** (allow explicitly, as in m9); check ownership on every object access ("is this row this user's?"); and don't trust IDs, roles, or "admin=true" coming from the client. Hiding an admin page without protecting its endpoint is not access control.

**Build-task tie-in.** Pick an endpoint in your app that returns user-specific data. Ask: if I change the ID in the URL to another user's, does the server stop me? If the only thing stopping me is that the UI didn't show the link, that's a broken-access-control bug waiting to be found.

**Check (mastery bar for m4).** Learner can explain injection and its fix in one sentence, AND explain broken access control as a missing/weak "are you allowed?" check that must be enforced on the server, not just hidden in the UI.
