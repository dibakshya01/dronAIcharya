# m5 — Build it with AI (the main event)

## L1 — Tracer bullet: the thinnest end-to-end slice first

**Concept.** A **tracer bullet** is one skinny slice of your app that goes *all the way through every layer* — a button → it saves one thing → that thing shows back on screen — built before anything wide or pretty. The point is to prove the whole path connects and to flush out the scary unknowns *early*, while the app is still tiny and easy to change. Width comes later; the connected path comes first.

**ELI5.** Before building a whole house, you run a single wire from the street to one light bulb and flip the switch. If it lights, the power path works and you can confidently add rooms. If it doesn't, you found out while there was only one wire to fix.

**Build-task tie-in.** For the habit tracker, the tracer bullet is: type a habit, press add, it gets stored, it appears in the list. No styling, no extra features — just the entire path working once, end to end.

**Under the hood.** This is step three of dronAIcharya's build method (spec → design → *tracer bullet* → layer by layer). We de-risk the connections first on purpose. The classic beginner trap is "wide before deep" — a beautiful front end wired to nothing.

**Check.** Learner can say what a tracer bullet is and why thin-but-end-to-end comes before building wide.

---

## L2 — Driving the AI to build a layer, reviewing each change

**Concept.** After the tracer bullet, you grow the app **layer by layer** (data → logic → integration → UI), **one small change at a time**. *You* drive: ask for one layer, read what the AI changed, approve or correct it, then move to the next. You never accept a giant pile of code you haven't looked at. Every file edit is a visible tool call — treat it like a change you're signing off on.

**ELI5.** Like a contractor showing you each finished room before starting the next — not handing you keys to a whole house you never walked through.

**Build-task tie-in.** We add the tracker's pieces in order — storage first, then the add/delete logic, then the list on screen — looking at each change before asking for the next one.

**Under the hood.** Small changes mean a small blast radius: if something breaks, you know *which* change did it. This pairs directly with committing often (L4) and with debugging (m7) — both are far easier when each step was small.

**Check.** Learner can say why building and reviewing one small change at a time beats accepting one big code dump.

---

## L3 — Running your app and reading what happened

**Concept.** A feature isn't done until you **run it and watch it behave**. You start the app, do the thing, and read the output — the screen, the terminal, the logs. Running is how "the AI says it works" becomes "I saw it work." And errors when you run are normal and *useful* — they're the next lesson, not a failure.

**ELI5.** A recipe isn't proven by reading it. You cook the dish and taste it. Code is the same: reading it is a guess; running it is the truth.

**Build-task tie-in.** We run the tracker on your machine, add a habit, refresh the page, and confirm it survived. If it didn't, congratulations — you just found your first real bug to fix.

**Under the hood.** "It runs on my machine" means a local development server is serving the app to your browser. The terminal output and the browser are your instruments — things to read, not to fear.

**Check.** Learner knows that running the app and observing it (not just reading the code) is what proves a slice actually works.

---

## L4 — Iterating: small steps, commit often

**Concept.** You grow the app in small steps, and after each step that *works*, you **commit** — save a snapshot in version control. Committing often means you always have a recent known-good point to return to if the next change breaks things. The rhythm is: small step → see it work → commit → next step.

**ELI5.** Like checkpoints in a video game. When you die, you don't replay the whole level — you restart from the last checkpoint. Commits are checkpoints for your code.

**Build-task tie-in.** Each time the tracker gains a working feature, we commit with a short message like "add delete button." The full git details come in m9; the *habit* starts right here.

**Under the hood.** A commit is a labeled snapshot of all your files at that moment. "Commit often" pairs with "small changes" so every snapshot is easy to understand and safe to roll back to — which is exactly what rescues you from a debugging loop (m7).

**Check (mastery bar for m5).** Learner has a running app with a working end-to-end slice (the tracer bullet) they can explain in their own words, and has committed at least one working step.
