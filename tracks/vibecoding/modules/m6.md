# m6 — Reading & trusting AI output

## L1 — Reading code you didn't write

**Concept.** You don't need to understand every line to review generated code usefully. Look for three things: **(1)** does the *shape* match what you asked — the right pieces, roughly where you'd expect them? **(2)** do the *names* make sense — a function called `deleteHabit` should delete a habit, not send an email? **(3)** does it touch anything that matters — your data, files, money, or secrets? Skim the plumbing; read closely the parts that can hurt you.

**ELI5.** It's like checking a contractor's work. You don't re-pour the concrete yourself, but you do check that the doors open, the taps run, and nothing's on fire.

**Build-task tie-in.** When the AI adds the tracker's delete feature, we read the delete logic carefully (it removes data) and only skim the boilerplate around it.

**Under the hood.** You can always ask the AI to explain its own code in plain language — but then sanity-check that explanation against the code you can see. The code is the truth; the summary is just a prediction about it.

**Check.** Learner can name what to focus on when reading code they didn't write.

---

## L2 — The trust checklist

**Concept.** Before you rely on a piece of generated code, run three checks, in this order: **(1) Does it run?** — no errors when you actually execute it. **(2) Is it safe?** — no secrets hard-coded, nothing deleting or sending things you didn't intend, no obvious hole. **(3) Does it do what the spec says?** — it meets the acceptance criteria you wrote in m4. Runs, safe, correct. All three.

**ELI5.** Like checking a car before a trip: does it start, are the brakes okay, and does it actually go where you steer? A car that starts but won't steer still fails.

**Build-task tie-in.** For each tracker feature we run it, glance for anything sketchy, and tick it against the spec's acceptance criteria before moving on.

**Check.** Learner can list the three trust checks: it runs, it's safe, and it matches the spec.

## L3 — Spotting an invented API or a plausible-but-wrong answer

**Concept.** Because the model predicts *plausible* text (m1), it can invent things that look completely real — a function that doesn't exist, a library option that was never a thing, a config key someone made up. They arrive confident and well-formatted, which is exactly why they fool people. The tells: it errors when you run it ("no such function"), the real docs don't mention it, or it's suspiciously perfect for your exact niche need.

**ELI5.** Like a very fluent tour guide who, rather than admit "I don't know," invents a convincing street name. It sounds right and leads nowhere.

**Deep dive (optional).** The fix is **grounding**: give the model the real documentation, or let it fetch the docs with a tool, and then *run the code*. Invented APIs die the instant you execute them — which is why "does it run" is check #1. The highest-risk zone is brand-new or obscure libraries, where the model's training may be thin or out of date (the knowledge cutoff, m1 L2).

**Build-task tie-in.** If a library call for the tracker errors with "is not a function," we treat it as a likely hallucination and check the real docs — rather than arguing with the model, which will happily invent a second wrong answer.

**Check (mastery bar for m6).** Learner can list at least two things to check before trusting generated code, and can describe how an invented API usually reveals itself.
