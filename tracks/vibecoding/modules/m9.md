# m9 — Ship it

## L1 — Git & GitHub basics (save points you can share and roll back to)

**Concept.** **Git** is a tool that records snapshots of your project called **commits**. Each commit is a save point you can return to, and the history shows what changed and when. **GitHub** is a website that hosts a copy of your git repository online — so it's backed up, shareable by link, and reachable by other people (or future-you on another machine). The core moves: *commit* (save a snapshot locally), *push* (send your commits up to GitHub), *pull* / *clone* (get them back down).

**ELI5.** Git is the "save game" button *with a full history of every save*. GitHub is uploading those saves to the cloud, so you can't lose them and can share the link with a friend.

**Deep dive (optional).** Commits form a timeline you can **branch** (try something risky on a side branch, merge it if it works, throw it away if it doesn't) and **roll back** (return to an earlier commit when a change breaks things). This is why "commit often" from m5 is so powerful: more save points mean safer experiments.

**Build-task tie-in.** We put the tracker in git — it already has commits from m5 — then create a GitHub repository and push to it. Now your work is backed up and you have a link you could send anyone.

**Under the hood.** The repository lives on *your* disk. GitHub is just a remote copy that your local one syncs with. Nothing leaves your machine until you choose to `push`.

**Check.** Learner can say a commit is a save point you can roll back to, and GitHub is the online, shareable/backup copy of the repo.

## L2 — Secrets & keys: what never goes in the repo

**Concept.** **Secrets** — API keys, passwords, tokens, database URLs — must **never** be committed to the repo. Anyone who can see the repo (and on *public* GitHub, that's everyone) could read them and use them, often costing you money or access. Secrets live in a separate file (commonly a `.env` file) that is listed in `.gitignore` so git never tracks it. The code reads the secret from the environment at runtime; the repo holds the *code*, never the secret value.

**ELI5.** Your code is the lock; the key is the secret. You can happily share the blueprint of the lock — but you never tape the key to the front door.

**Build-task tie-in.** If the tracker ever needs a key, we put it in a `.env` file, add `.env` to `.gitignore`, and confirm it isn't in what we push.

**Under the hood (important).** Git remembers *history*. If a secret is ever committed, deleting it in a later commit does **not** remove it from the past — it's still sitting in the history, recoverable. The real fix is to **revoke/rotate** that key immediately (make the old one invalid) and issue a new one. That's exactly why we keep secrets out from the very first commit.

**Check.** Learner can say secrets go in an ignored file (not the repo), and that a leaked key must be rotated/revoked, not just deleted.

## L3 — Deploy: getting it on the internet (prep up to your click)

**Concept.** **Deploying** means putting your app on a server so it has a public URL anyone can visit, instead of only running on your machine. The common modern path: your code is on GitHub, you connect a hosting platform to that repo, it builds and runs your app, and it hands you a URL. Secrets are set in the host's dashboard as **environment variables** — never in the repo. dronAIcharya does all the prep (config, build settings, a checklist), but the final "deploy / authorize / connect my account" click is **yours**.

**ELI5.** dronAIcharya packs the suitcase and drives you to the airport; *you* show your passport and board. The irreversible, account-linked step is yours by design.

**Deep dive (optional).** Hosts usually **redeploy automatically every time you push to GitHub**, so your git habit and your deploy become one smooth flow. Static sites (just files) and small apps often have free tiers; anything with a backend or database needs its secrets configured on the host first. (The exact platforms, free tiers, and dashboards change often — the *shape* stays the same: connect the repo → set the env vars → deploy.)

**Build-task tie-in.** We prepare the tracker to deploy — confirm it builds, make sure secrets are external, check there's a start command — then hand you the final click that puts it live.

**Under the hood.** This is the same safety seam as m8: deploying is outward and public, a decision of consequence. So the human performs the last step. dronAIcharya preps; the human clicks.

**Check (mastery bar for m9).** The app is in version control with secrets kept out of the repo, and the learner can describe the deploy path — code on GitHub → a host builds from it → a public URL, with secrets set on the host — and that the final deploy click is theirs.
