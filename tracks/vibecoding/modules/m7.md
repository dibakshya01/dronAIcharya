# m7 — Debugging with AI

## L1 — Reading an error message (it's a clue, not a scolding)

**Concept.** An **error message** is the computer telling you precisely what went wrong and, usually, *where*. It's the most useful free information you get while building. Read it: what failed, which file and line, what it expected versus what it got. It is a clue pointing at the problem, not a judgment on you.

**ELI5.** It's like a dashboard warning light that also prints a sentence: "left rear tire, low pressure." Annoying, yes — but it's telling you exactly where to look.

**Build-task tie-in.** When the tracker throws an error, we read the message together first — the file, the line, the key phrase — *before* changing anything. Most fixes start with actually reading the error.

**Under the hood.** The "stack trace" is the chain of calls that led to the failure; the real culprit is usually at the top or the bottom of it. That same error text is also the single best thing you can hand the AI (next lesson).

**Check.** Learner treats an error as a readable clue (what failed, where) rather than noise to panic over.

---

## L2 — Giving the AI the right context to fix a bug

**Concept.** To fix a bug, the AI needs the same things a human would: the **exact error** (copied, not paraphrased), the **relevant code/file**, **what you did** to trigger it, and **what you expected** instead. "It's broken" gets a guess; "here's the error, here's the file, here's what I expected" gets a fix. This is m2's prompting, pointed at a bug.

**ELI5.** Like calling a plumber. "There's water somewhere" versus "the pipe under the kitchen sink drips when I run the hot tap." One of those gets a real fix on the first visit.

**Build-task tie-in.** We practice turning a tracker bug into a focused request: paste the exact error + the function involved + "I expected the habit to save, but it disappears when I refresh."

**Under the hood.** The error plus the code narrows the model's prediction down to *your* actual problem. Vague reports make it pattern-match to generic, often irrelevant fixes — because a vague prompt has many plausible continuations, and only a few are right.

**Check.** Learner can assemble the exact error + the relevant code + the expected behavior into one fix request.

---

## L3 — When the AI loops or guesses — how to break the cycle

**Concept.** Sometimes the AI tries a fix, it fails, it tries a nearly identical fix, it fails again — a **loop**. The signs: the same error keeps returning, or the changes get bigger and more speculative. Break it by *stopping*: roll back to a known-good commit, add real information (run it and read the actual output, add a log/print line), or reframe the problem. The cure for guessing is evidence, not more guesses.

**ELI5.** If someone keeps trying slightly different keys in a lock that won't open, the fix isn't a hundredth key — it's checking whether it's even the right door.

**Build-task tie-in.** If a tracker fix starts looping, we roll back to the last working commit (this is where m5's "commit often" habit pays off) and gather evidence before trying again.

**Under the hood.** The model guesses when it lacks information. Feeding it a real log, or a minimal reproduction of the bug, turns guessing into diagnosis. This is exactly why reading errors (L1) and committing often (m5) matter so much when things go wrong.

**Check (mastery bar for m7).** Learner can turn an error into a focused, context-rich fix request, and knows to break a guessing loop with fresh evidence or a rollback rather than more guesses.
