# m8 — Modules, packages & virtual environments

## L1 — `import`: using code someone already wrote

**Concept.** A **module** is a file of Python code you can reuse. Python ships with a huge **standard library** of them — ready to use, no install needed. You bring one in with `import`:

```python
import json                      # whole module
data = json.dumps(tasks)         # use it with the module name

from datetime import date        # one name out of a module
today = date.today()
```

Your own `.py` files are modules too: split the todo app into `storage.py` and `todo.py`, and `todo.py` can `from storage import save_tasks`.

**ELI5.** You don't forge your own screwdriver to hang a picture — you grab one from the drawer. `import` opens the drawer and hands you a tool someone already built and tested. The standard library is a very well-stocked drawer that comes with Python.

**Deep dive (optional).** `import json` keeps the name tidy (`json.dumps`), making it obvious where a function came from; `from json import dumps` saves typing but can hide origins and cause name clashes — prefer the plain `import` when unsure. When you `import mymodule`, Python runs that file once, top to bottom, the first time it's imported, then remembers it. A subtle beginner trap: never name your own file the same as a module you import (e.g. `json.py`), or Python finds *yours* instead of the real one.

**Build-task tie-in.** We upgrade the todo app's storage from plain text to **JSON** using the standard-library `json` module — `json.dump(tasks, f)` and `json.load(f)` — which saves the whole list-of-dicts structure faithfully, not just flat lines. And we split the code into modules so each file has one job.

**Check.** Learner can import a standard-library module and use something from it, and explain that a module is just a reusable file of code.

## L2 — `pip` & packages

**Concept.** Beyond the standard library is a world of **third-party packages** — code published by other people on the Python Package Index (**PyPI**). You install one with **pip**, Python's package installer, from your terminal (not inside Python): `pip install requests`. After that you can `import requests` in your code like any module. `requests` (for web calls) and `pytest` (for tests) are two we'll install soon — both are third-party, so they need installing first.

**ELI5.** The standard library is the tools that come in the box. pip is the hardware store: `pip install X` drives over, buys tool X, and puts it in your drawer so you can use it. The store is PyPI; pip is the trip there.

**Deep dive (optional).** Because anyone can publish to PyPI, treat a package like any outside code: check it's the one you meant (typo-squatting is a real attack — `reqeusts` is not `requests`), see that it's widely used and maintained, and be honest that installing it runs *their* code on your machine. `pip install X` grabs the latest version; pinning an exact version (`requests==2.32.3`) makes your project reproducible. `pip list` shows what's installed.

**Build-task tie-in.** The weather fetcher (m9) needs `requests`, and our tests (m10) need `pytest`. We'll `pip install` both — but *where* they get installed is the point of the next lesson, and getting that wrong is the most common environment headache beginners hit.

**Check.** Learner can say what pip does and where it runs (the terminal), and that `import requests` only works after `pip install requests`.

## L3 — Virtual environments & why isolation matters

**Concept.** A **virtual environment** (venv) is a private, per-project sandbox for packages. You create one and activate it, and from then on `pip install` puts packages *there*, not system-wide:

```
python3 -m venv .venv          # create it (a folder named .venv)
source .venv/bin/activate      # turn it on (macOS/Linux)
.venv\Scripts\activate         # turn it on (Windows)
pip install requests           # installs into THIS project only
```

Each project gets its own venv, so their package versions never collide.

**ELI5.** A venv is a clean workbench for one project. Project A can keep an old version of a tool and project B a new one, each on its own bench, without them fighting over the shared garage. Activating a venv means "work at this bench now."

**Deep dive (optional).** Without a venv, every project shares one global set of packages, so upgrading a tool for project A can silently break project B — "dependency hell." The venv is just a folder holding its own Python and packages; activating it puts that folder first on your PATH. Record what a project needs in `requirements.txt` (`pip freeze > requirements.txt`) so anyone can rebuild the same environment with `pip install -r requirements.txt`. Don't commit the `.venv` folder to git — commit the `requirements.txt` instead.

**Build-task tie-in.** Before installing `requests` and `pytest`, we create and activate a venv for the todo project and write a `requirements.txt`. Now the project is self-contained: someone else can clone it, make their own venv, install the listed packages, and run it exactly as you do.

**Under the hood.** A venv is mostly a folder with its own `bin`/`Scripts` directory and a link back to a base Python. Activating it prepends that directory to your PATH, so typing `python` and `pip` finds the venv's copies first — which is why the *same* `pip install` command lands packages in different places depending on whether a venv is active. "Is my venv activated?" is the first question to ask when an import mysteriously fails.

**Check (mastery bar for m8).** Learner can import from the standard library, create and activate a venv, install a package into it with pip, and explain why isolation matters (projects need different versions without clashing).
