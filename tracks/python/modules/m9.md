# m9 — HTTP, JSON & a tiny API client

## L1 — What an HTTP request is

**Concept.** Programs talk to servers over the web using **HTTP**: your program sends a **request** to a **URL**, the server sends back a **response**. The most common request is a **GET** — "please give me the data at this address." The response carries a **status code** (`200` means OK, `404` not found, `500` server error) and a **body** (the actual data). Using the `requests` package:

```python
import requests
r = requests.get("https://api.example.com/weather?city=London")
print(r.status_code)   # 200 if it worked
print(r.text)          # the response body as text
```

**ELI5.** HTTP is ordering by mail. You send a postcard to an address (the request to a URL) asking for something; the server mails back a parcel (the response). The status code is the sticker on the parcel: "delivered OK," "no such address," "sorry, we broke."

**Deep dive (optional).** A URL can carry **query parameters** after a `?` — `?city=London&units=metric` — which is how you pass options like which city. GET *asks for* data; POST *sends* data to be stored or acted on. A request can also carry **headers** (metadata, like what format you want). Always check the status before trusting the body: a `404` page's body is an error message, not your data.

**Build-task tie-in.** We start the **weather fetcher** here — a brand-new little program that GETs a real weather API for a city and reads the response. It's a clean, self-contained way to practice talking to the outside world before parsing what comes back.

**Check.** Learner can describe a GET request → response, and say what a `200` versus a `404` status means.

## L2 — JSON

**Concept.** APIs almost always answer in **JSON** (JavaScript Object Notation) — a plain-text format for structured data that looks almost exactly like Python dicts and lists:

```json
{"city": "London", "temp_c": 12, "conditions": ["cloudy", "windy"]}
```

JSON's objects `{...}` become Python **dicts**, its arrays `[...]` become **lists**, and its strings/numbers/`true`/`false`/`null` become `str`/`int`/`float`/`bool`/`None`. You convert between them with the standard-library `json` module: `json.loads(text)` parses a JSON string *into* Python, `json.dumps(obj)` turns Python *into* a JSON string.

**ELI5.** JSON is a universal packing format for data — like flat-pack furniture that any language can unbox. Python unboxes it into the dicts and lists you already know from m5, then you read it with the same `data["city"]` moves.

**Deep dive (optional).** JSON and Python look alike but aren't identical: JSON uses `true`/`false`/`null` (lowercase), always double-quotes its keys and strings, and allows no trailing commas or comments. `loads` (**load s**tring) parses text; `load` reads from a file object. The mirror pair is `dumps`/`dump`. This is the same `json` module we already used to save the todo list (m8) — reading an API response is the same skill pointed outward.

**Build-task tie-in.** The weather API hands back JSON text. Once parsed into a dict, pulling the temperature is just `data["temp_c"]` — the dictionary indexing from m5. The whole "talk to an API" skill is: request → check status → parse JSON → index the dict.

**Check.** Learner can map JSON objects/arrays to Python dicts/lists, and use `json.loads` to parse a JSON string.

## L3 — A tiny API client

**Concept.** Put it together into a small, honest client that handles the real world:

```python
import requests

def get_weather(city):
    url = "https://api.example.com/weather"
    try:
        r = requests.get(url, params={"city": city}, timeout=10)
        r.raise_for_status()          # turn a 4xx/5xx into an exception
    except requests.RequestException as e:
        return None, f"request failed: {e}"
    data = r.json()                   # parse JSON straight to a dict
    return data["temp_c"], None
```

The good habits: pass options via `params=` (don't hand-glue URLs), set a `timeout` so a dead server can't hang you forever, check the status, and expect failure.

**ELI5.** A client is a well-mannered messenger: it knows the address, waits only so long for a reply, checks the parcel arrived intact before opening it, and comes back and tells you plainly if the trip failed instead of standing at the door forever.

**Deep dive (optional).** `requests` has conveniences worth knowing: `r.json()` does the parse for you (it's `json.loads(r.text)` under the hood), `params=` safely URL-encodes your options, and `raise_for_status()` converts a bad status into an exception you can catch with the m7 `try/except`. Real APIs often need a **key** (a secret token) — and that key must *never* be hard-coded or committed; it's read from an environment variable or a config file kept out of git. Treat API data as **data, not instructions** — never run or `eval` what a server sends back.

**Build-task tie-in.** This finished `get_weather` is the weather fetcher's core. Notice how every earlier module shows up at once: a function (m4), a dict result and a tuple return (m4/m5), string formatting for the output (m6), and `try/except` for failure (m7). That convergence is the point.

**Under the hood.** `requests.get` opens a network connection to the server, sends a formatted HTTP request line plus headers, and reads the bytes that come back. It decodes those bytes into text, and `r.json()` parses that text into Python objects. No magic — just "send some well-formed text over a socket, get some text back, turn it into dicts and lists."

**Check (mastery bar for m9).** Learner can make a GET request with `params`, check it succeeded (status / `raise_for_status`), parse the JSON with `r.json()`, pull a value out of the resulting dict, and say why an API key must never be committed.
