# m4 — Functions

## L1 — Why functions exist

**Concept.** A **function** is a named chunk of code you can run whenever you want by calling its name. You **define** it once with `def`, then **call** it as many times as you like:

```python
def greet():
    print("Hello!")

greet()   # runs the body; prints Hello!
greet()   # runs it again
```

Functions exist so you can name a piece of work, reuse it without copying, and read your program as a list of intentions (`add_task()`, `save_tasks()`) instead of a wall of detail.

**ELI5.** A function is a recipe card. Writing the card (`def`) doesn't cook anything; it just records the steps under a name. Calling the function (`greet()`) is handing the card to the cook and saying "make this now." One card, cooked as often as you like.

**Deep dive (optional).** The parentheses are what *call* the function. `greet` (no parentheses) is the recipe card itself — the function as a value you could pass around. `greet()` (with parentheses) means "run it now." Forgetting the parentheses is a common early surprise: nothing happens, because you named the function instead of calling it.

**Build-task tie-in.** The todo app grows messy as one long script. Functions tidy it: `add_task(...)`, `list_tasks(...)`, `complete_task(...)`. The main loop then reads like plain English and each job lives in one place.

**Check.** Learner can define a function with `def` and call it, and explain that defining is not the same as calling.

## L2 — Parameters, arguments & `return`

**Concept.** A function becomes useful when you feed it data and get an answer back. **Parameters** are the named inputs in the definition; **arguments** are the actual values you pass when calling. **`return`** hands a value back to whoever called the function:

```python
def add(a, b):      # a and b are parameters
    return a + b    # hand the result back

total = add(2, 3)   # 2 and 3 are arguments; total is now 5
```

`return` also *ends* the function immediately. A function with no `return` hands back `None` (Python's "nothing" value).

**ELI5.** Parameters are the blanks on the recipe card ("add ___ eggs"). Arguments are what you write in the blanks when you cook ("2 eggs"). `return` is the finished dish handed back to you — as opposed to `print`, which just shouts the result into the room and keeps nothing.

**Deep dive (optional).** The crucial distinction: **`print` shows a value; `return` gives it back to the program.** `add(2, 3)` that only *prints* the total can't be used in `total = add(2, 3)` — `total` would be `None`, because the function returned nothing. Return when the caller needs the value for more work; print only when a human needs to read it.

**Build-task tie-in.** `add_task(tasks, text)` should *return* the updated task count so the app can say "you now have 4 tasks," while `list_tasks(tasks)` only *prints* and returns nothing — it exists for the human to read. Deciding "print or return?" for each todo function is the real lesson here.

**Check.** Learner can write a function with parameters that returns a value, and explain the difference between printing and returning.

## L3 — Scope

**Concept.** **Scope** is the region of a program where a name is visible. A variable created *inside* a function is **local**: it exists only while the function runs and vanishes when it returns. Code outside the function can't see it. A variable defined at the top level of the file is **global** and can be read from inside functions. This keeps functions tidy and independent — each has its own little workspace.

```python
def tally():
    count = 0      # local: only exists inside tally
    count = count + 1
    return count

tally()
print(count)       # ERROR: count is not defined out here
```

**ELI5.** Each function works at its own desk. Scratch paper on that desk (local variables) gets thrown out when the function finishes, and nobody at another desk can read it. That's a feature: two functions can both use a variable called `count` without clashing.

**Deep dive (optional).** A function can *read* a global, but assigning to a name inside a function makes a new local by default (so it won't accidentally clobber the global). The clean way to share data is parameters in and `return` out, not globals — passing `tasks` into each function keeps the data flow visible instead of hidden. Watch the mutable-argument subtlety: if you pass a list into a function and the function changes the list's contents, the caller sees the change, because both names point at the same list (m5 explains why).

**Build-task tie-in.** We pass `tasks` into every todo function rather than relying on a global. That's why `add_task(tasks, text)` takes `tasks` as a parameter: the data flows in and out on purpose, so you can always see where the task list is being touched.

**Under the hood.** When you call a function, Python creates a temporary **frame** — a fresh workspace holding that call's local variables. The frame is pushed onto the **call stack**; when the function returns, its frame is popped off and its locals are gone. Nested calls stack frames on top of each other, which is exactly what a stack trace shows you when something breaks.

**Check (mastery bar for m4).** Learner can write a function that takes arguments and returns a value, explain print vs. return, and say that a variable made inside a function is local and disappears when the function ends.
