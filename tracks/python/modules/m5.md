# m5 — Data structures

## L1 — Lists

**Concept.** A **list** is an ordered, changeable collection of values, written in square brackets: `tasks = ["buy milk", "call Sam"]`. Items keep their order and are reached by **index** (position), starting at `0`: `tasks[0]` is `"buy milk"`. You can change a list after making it: `tasks.append("water plants")` adds to the end, `tasks[0] = "buy bread"` replaces an item, `tasks.remove("call Sam")` deletes one. `len(tasks)` gives how many items.

**ELI5.** A list is a numbered row of lockers. Locker numbering starts at 0, so the first locker is number 0. You can put things in, swap them out, and add more lockers on the end whenever you like.

**Deep dive (optional).** Two traps. First, **list methods that change the list return `None`**: `x = tasks.append("y")` leaves `x` as `None`, because `append` modifies `tasks` in place and hands nothing back. Second, **aliasing**: `b = a` does not copy the list — both names point at the *same* list, so `b.append(9)` also changes `a`. To get an independent copy, use `b = a.copy()` (or `b = a[:]`).

**Build-task tie-in.** The todo app's tasks live in a list. `add_task` does `tasks.append(...)`; `list_tasks` loops over it; completing a task updates an item. The aliasing rule is why passing `tasks` into a function lets that function change the real list (m4's "mutable argument" note).

**Check.** Learner can make a list, read `list[0]`, append an item, and explain that indexing starts at 0.

## L2 — Tuples

**Concept.** A **tuple** is like a list but **immutable** — once made, it can't be changed. It's written with parentheses (or just commas): `point = (3, 4)`. You index it the same way (`point[0]` is `3`), but `point[0] = 9` is an error. Use a tuple for a fixed group of values that belong together and shouldn't change — coordinates, a row of data, a function returning several values at once.

**ELI5.** A list is a whiteboard you keep editing; a tuple is the same row of values set in stone. You reach for the stone version when the grouping is meant to stay put.

**Deep dive (optional).** Tuples let a function return several values cleanly: `return x, y` packs them into a tuple, and `a, b = get_point()` unpacks them back out. Because a tuple can't change, it's safe to use as a dictionary key (next lesson) while a list cannot be. "Immutable" is the same property that makes strings safe to share (m6).

**Build-task tie-in.** When a todo function needs to hand back two things at once — say, the updated count *and* a status message — returning them as a tuple (`return count, "added"`) is the natural move, then the caller unpacks: `count, msg = add_task(...)`.

**Check.** Learner can make a tuple and explain how it differs from a list (fixed vs. changeable).

## L3 — Dictionaries

**Concept.** A **dictionary** (`dict`) stores **key → value** pairs, so you look things up by a meaningful key instead of a numeric position. Written with curly braces and colons:

```python
task = {"text": "buy milk", "done": False, "priority": 2}
task["text"]          # "buy milk"
task["done"] = True   # update a value
task["tag"] = "home"  # add a new pair
```

Use a dict when each piece of data has a *name*, not just a position.

**ELI5.** A list answers "what's in slot 3?" A dictionary answers "what's the `priority`?" It's a labelled drawer set: you open the drawer by its label, not by counting from the left.

**Deep dive (optional).** Reaching for a missing key with `task["nope"]` raises `KeyError` and crashes. When a key might be absent, use `task.get("nope")` (returns `None`) or `task.get("nope", 0)` (returns a default). Loop with `for key in task:` for keys, or `for key, value in task.items():` for both. Keys must be immutable (a string, number, or tuple — not a list).

**Build-task tie-in.** This is the upgrade that makes the todo app real: instead of each task being just a string, each becomes a dict — `{"text": ..., "done": ..., "priority": ...}` — and `tasks` becomes a *list of dicts*. Now a task can be marked done without losing its text.

**Check.** Learner can make a dict, read and set values by key, and say when a dict beats a list (named data vs. positional).

## L4 — Sets & choosing the right structure

**Concept.** A **set** is an unordered collection with **no duplicates**, written `{1, 2, 3}`. Adding something already present changes nothing, so sets are perfect for "unique things" and fast membership tests (`"home" in tags`). Now the whole picture — pick by the job:
- **list** — ordered, changeable, duplicates allowed. Default for "a sequence of things."
- **tuple** — ordered, fixed. A grouping that shouldn't change.
- **dict** — look up values by a named key. Each item has fields.
- **set** — unique, unordered. "Which distinct things appear?" and fast "is it in here?"

**ELI5.** A set is a bag where identical items merge into one — throw in two "home" tags and the bag still holds one "home." It doesn't remember order; it only remembers *what's in it*.

**Deep dive (optional).** `{}` makes an empty *dict*, not a set — the empty set is `set()`, a genuine gotcha. Sets also do math: `a & b` (in both), `a | b` (in either), `a - b` (in a, not b). Membership (`x in s`) is near-instant for a set but gets slower for a long list, because a set is built for lookup.

**Build-task tie-in.** Tags on a task are a natural set: a task is either tagged `home` or it isn't, and you don't want `home` listed twice. And across the app, "which tags exist anywhere?" is a set union of every task's tags.

**Under the hood.** Dicts and sets are backed by a **hash table**: the key is run through a hash function to compute roughly where to store it, so lookup jumps near-straight to the spot instead of scanning every item. That's why `in` is fast for them and why their keys/members must be immutable (hashable) — the hash has to stay stable.

**Check (mastery bar for m5).** Learner can, for a given need, pick list / tuple / dict / set and justify it (order? changeable? named lookup? uniqueness?), and knows `{}` is an empty dict while `set()` is an empty set.
