# m7 — Files & errors

## L1 — Reading & writing files with `open` and `with`

**Concept.** To make data survive after the program ends, you save it to a **file** on disk. `open(path, mode)` gives you a file object; the **mode** says what you're doing: `"r"` read, `"w"` write (replaces the whole file), `"a"` append (add to the end). You read with `.read()` or by looping lines, and write with `.write(...)`. Always use a `with` block so the file is closed automatically when you're done:

```python
with open("tasks.txt", "w") as f:
    f.write("buy milk\n")

with open("tasks.txt", "r") as f:
    contents = f.read()
```

**ELI5.** A file is a notebook on the shelf; your program is a reader who takes it down. `with` is the polite rule "whoever opens the notebook puts it back" — it closes the file for you even if something goes wrong mid-way, so you never leave it lying open.

**Deep dive (optional).** `"w"` is destructive: it empties the file before writing, so opening with `"w"` and writing nothing wipes it. Use `"a"` to add without erasing. `\n` is the newline character — without it, everything runs onto one line. Looping is the memory-friendly way to read a big file line by line: `for line in f:` hands you one line at a time instead of loading the whole thing. Paths are relative to where you *run* the program, which is a common "file not found" surprise.

**Build-task tie-in.** This is what makes the todo app stick: `save_tasks(tasks)` writes every task to `tasks.txt`, and `load_tasks()` reads them back when the app starts. Now your list survives closing the program — the feature that turns a toy into a tool.

**Check.** Learner can write to a file and read it back using `with open(...)`, and say why `with` is preferred (it closes the file automatically).

## L2 — `try` / `except`

**Concept.** Some things fail at runtime no matter how careful you are: the file doesn't exist, the user types letters where you expected a number, the network is down. When Python hits such a problem it **raises an exception**, and unless you handle it the program crashes. `try` / `except` lets you attempt risky code and react instead of crashing:

```python
try:
    tasks = load_tasks()
except FileNotFoundError:
    tasks = []   # first run, no file yet — start empty
```

**ELI5.** `try` means "attempt this, it might go wrong." `except` is the safety net that catches a specific kind of fall and decides what to do, instead of letting the whole program hit the floor.

**Deep dive (optional).** **Catch specific exceptions, not everything.** A bare `except:` swallows *every* error — including your own typos, Ctrl-C (`KeyboardInterrupt`), and `SystemExit` — and hides real bugs behind a calm face. Even `except Exception:` is usually too broad (it still catches your typos, though not Ctrl-C/SystemExit, which aren't `Exception` subclasses). Name the one you expect: `except FileNotFoundError`, `except ValueError`. You can add `else:` (ran if no error) and `finally:` (always runs, error or not — good for cleanup). Catch narrowly; let the unexpected surface.

**Build-task tie-in.** Two real spots in the todo app: loading tasks when `tasks.txt` doesn't exist yet (`except FileNotFoundError`), and reading a priority the user typed (`except ValueError` when `int(input(...))` gets `"abc"`). Both turn a crash into a graceful "start fresh" or "please type a number."

**Check.** Learner can wrap risky code in `try/except` catching a specific exception, and say why a bare `except:` is a bad idea.

## L3 — Exceptions as signals, not scoldings

**Concept.** An exception isn't the language telling you off — it's a precise **signal** about what went wrong and where. The error's **type** (`ValueError`, `KeyError`, `FileNotFoundError`) names the category; its **message** gives the detail; the **traceback** is the trail of function calls leading to the failure, with the deepest, most relevant line usually at the bottom. Read it as a clue, not a verdict.

**ELI5.** A smoke alarm isn't angry at you; it's pointing at the kitchen. An exception points at the exact line and reason your program tripped. Read the last line first — that's usually where it actually caught fire.

**Deep dive (optional).** You can raise your own signals with `raise ValueError("priority must be 1-3")`, which is how functions report bad input to their callers. Exceptions travel *up* the call stack until something catches them, so you can handle an error far from where it happened. This is the mirror image of `return`: a value flows back up on success, an exception flows back up on failure. Choosing the *right* exception type (and sometimes letting it crash loudly during development) is part of honest programming — don't hide a problem you don't actually understand yet.

**Build-task tie-in.** If someone calls `complete_task(tasks, 99)` but there are only 3 tasks, raising a clear `ValueError("no task number 99")` beats silently doing nothing — the caller gets a real signal it can show the user. We'll add exactly that guard.

**Under the hood.** When an exception is raised, Python stops normal execution and unwinds the call stack frame by frame (m4), looking for a matching `except` at each level. If it reaches the top with no handler, it prints the traceback — that frame-by-frame unwinding *is* the traceback you read — and exits. Nothing magic: it's the call stack in reverse.

**Check (mastery bar for m7).** Learner can read and write a file with `with`, catch a specific exception to avoid a crash, and explain that an exception is a typed signal (read the traceback bottom-up) rather than a punishment.
