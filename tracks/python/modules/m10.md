# m10 — Testing & a small real project, end to end

## L1 — `assert`: the smallest possible test

**Concept.** A **test** is code that checks your code does what you claim. The simplest form is `assert`: it states something you believe is true, and if it isn't, the program stops with an `AssertionError`.

```python
assert add_task([], "buy milk") == 1   # adding to empty list -> count 1
```

If `add_task` is correct, nothing happens. If it's broken, the assert fails loudly, pointing right at the wrong assumption. A test is just a claim about behaviour, checked automatically.

**ELI5.** An `assert` is a tripwire you set across the path: "I expect the count to be 1 here." As long as reality steps over it cleanly, you never notice. The moment the code misbehaves, the tripwire trips and tells you exactly which expectation broke.

**Deep dive (optional).** `assert condition, "message"` adds an explanation shown when it fails. Asserts are for *testing and sanity checks*, not for validating user input in real programs — Python can switch them off (running with `-O`), so never guard real logic with them. For checking what a user typed, raise a real exception (m7); for checking your own code's behaviour, assert away.

**Build-task tie-in.** Before trusting the todo functions, we write a handful of asserts: add raises the count, completing a task flips its `done` to `True`, saving then loading returns the same tasks. Each is one plain claim about the app's behaviour.

**Check.** Learner can write an `assert` that checks a function's result, and say what happens when it passes versus fails.

## L2 — pytest basics

**Concept.** Scattered asserts work, but **pytest** runs them for you, finds failures, and reports clearly. You write test *functions* named `test_...`, each containing asserts, in a file named `test_something.py`. Then you run `pytest` in the terminal and it discovers and runs them all:

```python
# test_todo.py
from todo import add_task, complete_task

def test_add_increases_count():
    tasks = []
    add_task(tasks, "buy milk")
    assert len(tasks) == 1

def test_complete_marks_done():
    tasks = []
    add_task(tasks, "buy milk")
    complete_task(tasks, 1)
    assert tasks[0]["done"] is True
```

`pytest` prints a green dot per pass and a full report for any failure. (pytest is third-party — `pip install pytest` into your venv first, from m8.)

**ELI5.** pytest is a checklist robot. You write down each "it should do X" as a little function; the robot runs every one, ticks the ones that pass, and hands you a detailed note on any that fail. You stop checking by hand.

**Deep dive (optional).** Good tests are independent (each builds its own fresh data, so order doesn't matter) and named for the behaviour they check, so a failure name tells you what broke. Test the **contract** — given this input, expect this output — not the internal details, so you can refactor freely. A great habit: when you find a bug, first write a test that fails *because* of it, then fix the code until the test goes green. That test now guards against the bug ever returning.

**Build-task tie-in.** We turn the m10 asserts into a real `test_todo.py` and run `pytest`. From now on, every change to the todo app is followed by `pytest` — a ten-second confirmation that nothing you relied on broke.

**Check.** Learner can write a `test_...` function with an assert and run it with `pytest`, and explain why each test should set up its own data.

## L3 — Tying it together: the finished project

**Concept.** The todo app is now a real, small program with every piece you've learned, wired together:
- **values & types** (m2) for a task's fields; **control flow** (m3) for the menu loop;
- **functions** (m4) for each action; **list of dicts** (m5) as the data model;
- **strings/f-strings** (m6) for the display; **files + try/except** (m7) to save and load safely;
- **modules & a venv** (m8) to organise and isolate it; **JSON** (m8/m9) for storage and for the optional weather feature; and
- **pytest** (m10) proving it works.

That's the full arc from `print("hello")` to a tested, persistent, structured application — built and understood, not pasted.

**ELI5.** Every module handed you one brick. This lesson is standing back and seeing the wall: a program that remembers your tasks between runs, reacts to commands, fails gracefully, and has tests watching its back. You can point at any brick and say what it does and why it's there.

**Deep dive (optional).** Where to grow next, honestly: a **mini web API** (wrap the todo logic in a tiny web framework so other programs can call it over HTTP — the m9 skill turned around to *serve* requests); type hints (`def add_task(tasks: list, text: str) -> int:`) for clearer contracts; and a proper database instead of a JSON file once the data outgrows a single file. None of these are new mysteries — each is a known module's idea pushed one step further.

**Build-task tie-in.** Final checklist for the project: it runs from a clean venv (`pip install -r requirements.txt`), `pytest` is green, secrets (like any weather API key) live outside the repo, and a short README says how to run it. That is what "done and shippable" looks like for a small Python project.

**Under the hood.** Run the whole-track recap: `python3 todo.py` starts the interpreter, which reads and bytecode-compiles your file (m1); each function call pushes a frame on the call stack and pops it on return (m4); `import` runs each module once and caches it (m8); saving serialises your dicts to JSON text and loading parses it back (m8/m9); a web request is text over a socket turned into dicts (m9); and `pytest` simply calls your functions and checks the asserts (m10). No magic anywhere — just layers you can now name.

**Check (mastery bar for m10).** Learner can write a passing pytest test for one of their functions, run the suite green, and explain what a passing test proves (this input gives this output, for the cases you wrote) and what it does *not* prove (correctness for untested inputs) — and can give a one-line "under the hood" account of how their finished program runs.
